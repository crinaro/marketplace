# Changelog

Generated from fixes confirmed shipped — public reports and internal fixes alike, each verified against its release tag on the published remote; older releases after their push, the newest one by the publish that pushed it, so the section for the version you installed is in the file that came with it. Sections are grouped by plugin, then by version. Newest first.

## jobsearch 0.94.0
A role that meets your criteria is now shown to you for a pursue-or-pass decision whatever its company, and a run reads matching roles first, newest first. LinkedIn job search is its own step, scheduled within limits and stopped by any LinkedIn warning. On update, one automatic step marks your profile as needing jobsearch 0.94.0 or later, keeps a copy of each file it changes, and withdraws reads that a later failed read of the same page contradicts. Quit and reopen Claude after updating.
- Roles are judged on your criteria, not on whether you chose their company. A role at a company you have not decided on, or are only watching, that passes your own title, pay and place rules is read and screened, and if it still fits it is put to you to pursue or pass. A role that fails a rule stays held, with the rule that held it. A rule the plugin could not read never holds a role. A role at a company you passed on stays held and is counted as that. Your company choices now steer outreach and how often a company is checked, not whether a matching role is shown.
- Matching roles are read newest first, at most 20 a run (the setting `search.matching_roles_per_run`). Reading is paused while 25 role decisions are open (`search.open_decisions_max`), and the run says so. The roles released from the old company hold are not reported as failures.
- Pursuing a role makes its company a target, in the same step, with no motivation needed. A company you passed on, and a staffing firm or job board, is left alone, and the line printed says why. A company targeted this way does not bring its other roles in: only the ones that match. Passing on a role does not remove the target; the line printed says how.
- Every role row says why it is there, for example "matches Head of Widgets, 300-350K stated, remote, posted 2 days ago", and what was not read is said as not read, never guessed. The dashboard's Held roles section says why each role is held.
- A read must quote the posting. A read whose only quote is the title is refused and nothing is written. If a later read of the same page in the same run fails, the earlier read is withdrawn, and a read you can see is wrong can be withdrawn too: what it replaced is put back, the role is screened again, and the whole history is kept. A page that says "Not currently accepting applications" is read as closed. A page in another language is never read as closed by the script.
- A search whose filters LinkedIn dropped no longer discards roles whose cards state their setting. A dropped filter or a result cut short is counted as less coverage and holds no role. Each search reads the first page only, up to 25 results, and the rest are counted as not read. Queries not run are listed by title and place.
- LinkedIn search runs as its own step. A scheduled run searches when 48 hours have passed since the last search was started or reached (`search.linkedin_search_every_days`, 2 days unless you changed it, counted in hours, never by calendar day), so a run that crashed still uses up its turn. The limits are in the plugin's scripts, not only in the instructions: at most 20 searches a pass (`search.linkedin_queries_per_pass`), one page for each search, never a second, every page judged once, at most 25 job links from a search and 500 in a pass. It runs only when the first results page reads and your LinkedIn setting allows LinkedIn work in that run. When it does not search, the run says why and when it last did. Pages are opened in a fresh tab, one at a time, and closed. **No scheduled LinkedIn search runs until the update step below has run on your profile**; your next session runs it.
- **Any LinkedIn page the plugin is in doubt about counts as a warning, and a warning ends the search at once.** Every LinkedIn page it opens (a search page, a job posting, a reply page) is judged by a script, and only a page it positively recognises as an ordinary one is ordinary. A warning, a sign-in or security check, a CAPTCHA, or any doubt (a browser tool that fails or returns nothing counts) ends that pass with no retry, and a warning found by any run ends every run already under way at its next LinkedIn step. Scheduled search then stays off until you turn it back on. **What may therefore turn it off when nothing is wrong:** a search with no results, a LinkedIn layout change, a LinkedIn in a language other than English, a pop-up, toast or notice on an ordinary page, a banner, and a job description that itself uses a warning's words. **The reason is shown in words**, with a sentence saying so when it may only be a layout change or an empty search, at the start of every session, in every run summary and on the dashboard until you act. Open LinkedIn yourself and look, then tell Claude you have looked and name the warning's date; a turn-on dated before the warning it names is refused. Nothing else turns it back on: not time, not a later good search, not an update. You can still run the attended search.
- The first five scheduled searches print their counts (planned, read, cards, job ids, recorded, held, cut short, filters dropped, what stopped it) at your next start, so you can see them work.
- The browser works when the session is not on screen. Every browsing step opens each page in its own fresh tab at a fixed size and closes it. A LinkedIn page is read on its content, not on whether the browser is drawing it, and the pane's hidden or shown line is recorded but decides nothing. On a results page one read-only check takes each card's own link; nothing is clicked.
- No shipped text now says your mailbox gets no LinkedIn mail. Mail is one partial source.
- On update, one automatic step runs in your next session. It marks your profile as needing jobsearch 0.94.0 or later, keeps a copy of each file it changes (`data/opportunities.jsonl` and `data/pending_actions.jsonl`, each only if that file will change; a session with nothing to change keeps none), withdraws reads that a later failed read of the same page in the same run contradicts (never on a role you already decided, at most 50 a session), and releases held capture items that their cards now answer. **Copy rule:** the copy is `.pre-0.94.0`; if one is already there it is used only when it holds every row about to change exactly, and otherwise the originals go to a new copy named `.pre-0.94.0.1`, then `.2` and so on, and the message names which copy holds them. If a file cannot be read it says so, writes nothing and runs again next session. To undo it, put back the copy the message names; the mark stays. Another machine that shares your profile and runs 0.93 or earlier stops at the mark until you update it.
- Not yet, or not perfect: several searches in one run are untested, and only two LinkedIn results pages and one posting have been read live by a scheduled session. How often an ordinary page is taken for a warning (see above) has not been measured, so scheduled search may turn off more often than it should until the wording is seen. A warning drawn inside the page's main area, header or side panel with no usual wording and no pop-up or notice would be missed, and so would one on a page with no language marked or one that is only an image; the plugin cannot prove that the browser step checks every page it opens, or guard against two checks at the same instant. A reply pass on an update-pending profile loses its LinkedIn search too. The description check may not match every posting layout. A filter LinkedIn drops is counted, not recovered. A company you are watching that already has a motivation is not targeted by a pursue.

## jobsearch 0.93.0
A new coverage report shows how well your resume versions and your LinkedIn profile match the roles you are pursuing, your resume's Word file now keeps the layout you give it, email you approve goes into your drafts with your resume attached, and sixteen problems you reported are fixed. On update, one automatic step marks your profile as needing jobsearch 0.93.0 or later and changes nothing else. Quit and reopen Claude after updating.
- /jobsearch:review-resume, /jobsearch:review-linkedin and the weekly review print the report. It shows six things. Lead title: whether each version's opening lines and your LinkedIn headline name one of your target titles, matched as whole words. Requirements: the requirements that keep coming up across the roles you are pursuing, which ones you are not aligned with, and which evidence sits in your claims file but on no version. Quantified bullets: how many bullets on each version carry a number. Results by version: reply and interview rates for each version you sent, shown only once it has gone out at least five times. Readability: whether the resume file is one column with no tables or text boxes. LinkedIn: whether your headline names a target title, and whether your skills cover your top recurring requirements. With the plugin's panel on, the report is a Coverage tab.
- The plugin never edits your LinkedIn profile, because LinkedIn's terms forbid software doing so. It proposes the text, you paste it, and you tell it the date you applied it. It keeps what you tell it your headline and skills are, and reads the live profile only when you ask in a session you are attending. The weekly review drafts copy only where the report shows a gap, supported by claims you have marked as public.
- Claude edits your resume versions for you, with no approval step, because they live in your own search folder; a scheduled weekly review applies the edits it proposes. It can import a resume from a Word, Markdown or text file into one of your versions. Every edit is checked, recorded so you can see and undo it, and put back if the check fails.
- Your resume's Word file keeps your layout. `record.py presence-docx` writes each version's Word file once, then updates only the words that changed, inside your own formatting: the spacing, text size and margins you set to make it fit the page are kept. A dated backup is taken before each update. If you changed the words in the Word file, nothing is overwritten: you are asked "Update the resume we keep on file from it? If not, your change will be overwritten at the next update." A scheduled run leaves that question in your approvals and changes neither file. A file the plugin cannot edit safely (tracked changes, tables or text boxes) is left alone, with what to do. With no remote repository the Word file stays on the computer that wrote it; with one it travels with your profile, and a file changed on two computers is asked about, never merged.
- Email you approve goes into your drafts; jobsearch never sends, and you always press Send. An email that says your resume is attached carries the Word file when you draft with gmail-multi 0.6.0, and the outbox records whether the draft really held it. The claude.ai Gmail, Fastmail and Superhuman connectors draft the message and print the file to attach yourself; with Microsoft 365, whose connector page names no draft tool, you draft it yourself and jobsearch says why. A resume version that fails its own check is never attached.
- Records: passing on a role you were pursuing now closes it in one step. A reply to someone whose conversation has no role can be recorded (`record.py answered contact:<id>`, or `person:<id>`). The weekly review reads held meetings from what you recorded, never from their scheduled status.
- Counts: people whose employment you have not confirmed count again in a target's known and contacted columns, flagged, and are never shown as a way in. The network mail line reads your sweep journal, so mailboxes swept every day show as covered. Weekly ask counts by kind match your touches. A draft older than `network.draft_unobserved_days` no longer uses up your weekly reach-out budget, and the strategy view shows owed drafts apart from what you spent. A new setting, `search.companies_raised_per_run`, sets how many companies a run raises for you to look into; unset, it follows `search.company_intake_per_run` as before. A draft whose heading holds a double quote no longer trips the dashboard's coverage check.
- Runs that failed quietly now say so: `brief.py` no longer hangs on a locked or unanswering credential store and names the credential it could not read; a sourcing channel no agent can reach is listed as UNREACHABLE with the step that reaches it; three LinkedIn passes in a row with the Browser pane hidden make the run say the LinkedIn sweep is not running, as blocking.
- Fewer false alarms: job-board and social digests are advisory in `reconcile --ats --verify`, and the follow-up check lists only inbound mail a re-run actually clears. Unmatched ATS mail is one question per sender domain per week. The purity check no longer flags every file when you track an employer named with one common English word, and the prose drift check no longer reads "the floor plus $X" as a second floor.
- Not yet, or not perfect: requirements researched before this release have no topic until an attended review assigns them (at most 60 rows, and only if you say yes). LinkedIn's headline and About length limits are not recorded. That the attachment really went into the draft is recorded from the session's copy of gmail-multi's reply, not checked by the plugin itself. If a draft call fails after it is staged, discard it and stage it again, which asks for your approval again. If another machine shares your profile and still runs 0.92 or earlier, update it: it stops at the 0.93.0 mark.

## jobsearch 0.92.0
The dashboard now shows what needs a decision from you, says why each row is there, and says plainly what each button does. On update, one automatic step marks your profile as needing jobsearch 0.92.0 or later and changes nothing else. Quit and reopen Claude after updating.
- Buttons copy text and record nothing until you paste it. Each now reads "Copy ... for N" (for example "Copy Yes for 10"), and after a click "Copied. Paste it into your jobsearch session in Claude Code." One note after Today says a plain claude.ai chat cannot record it. Targets rows list up to three role titles, the ones matching yours first. A company whose every sighting came through a recruiter is left out as a staffing firm, with a tick box under These are employers to undo it, and the sentence saying staffing firms are not listed appears only when that check could run.
- Each Network row says when the person wrote, the role it is about and whether that role is still open, and what a reply would serve. Someone who wrote back more than 60 days ago with no reply drafted is no longer listed (the network.reply_owed_days setting changes the 60), nor is a thread about a role that has ended. Everyone left out is named, with the reason, in one closed "Not listed" fold after Awaiting a reply. Two records that look like the same person show as one row marked "possible duplicate"; nothing is merged for you.
- You can stop following up with someone: ask the coordinator, which runs record.py stop-following with a dry run first. They leave They wrote back and Awaiting a reply until they write to you or you write to them, and their row then says they are back. --undo resumes.
- Roles held for a company decision have their own section, Roles waiting on a company decision: held roles whose title matches yours, role first, with the held count and its change since last week. Companies holding such a role are put to you first.
- The held count is recorded once per run, so the page can show how it moved since a week ago. The three caps between a find and a decision keep their order, and the page states them.
- The page keeps every role waiting on your decision in view: a held role that matches your titles is a row of its own, never only a number, and the dashboard's own check now fails if one goes missing or the held count does not add up.
- record.py set and set-in keep a note starting with [ or {, such as "[CLAUDE] checked", as text instead of crashing. A malformed object or list for a field that holds one is refused, naming the field.
- Not yet, or not perfect: the stop command names an open outbox message for the person but says nothing about a draft staged without one. The held count's weekly change appears only from seven days after your first 0.92.0 run. A message from the three days around a stop that is stored only after it brings the person back once; stop again if you still mean it. If another machine shares your profile and still runs 0.91, it refuses every command but can still regenerate and publish its own older page until you update it.

## jobsearch 0.91.0
A person now counts as your way in at a company only while they work there now, the weekly plan suggests ways in at companies where you have none, and you can choose to have jobsearch send an email for you after you approve it. Current employees only: on update, a migration first saves a copy of your people file (people.jsonl.pre-0.91.0), then marks each person linked to a company as current when you had an email from them at that company's domain in the last 180 days, and unknown otherwise. It never marks anyone as having left. Someone unknown is not counted at the company until you confirm them, so your reach counts will usually drop after the update; that is the change working, since until now everyone ever linked to a company was counted there. An attended run asks you about a few people at a time, or you can say it yourself with record.py employment (current, unknown or former). Companies where you have no way in: the weekly reach-out plan now suggests ways to build one, inside your existing weekly budget, including asking the company's recruiting team who you should speak with. Weekly counts show what you did; a reply rate appears only once at least five asks of a kind have been answered or closed over the past 12 weeks, and a week whose mail was not checked says not checked rather than a rate. A new onboarding question asks for your schools, bootcamps, past employers and communities, used only to point a lookup at people you share something with; the plugin never searches for anyone. If you have not answered it, an attended run asks again. Who does each outward act is now a setting, you (the default) or me. Email me is offered only when gmail-multi is your mail connector, and only in a session you are attending: you approve each message, Claude Code then asks you for that send, and an approval lapses after 10 minutes or in any other session. A scheduled or unattended run never sends; it queues the message for you. A message is marked sent only when it is found in your Sent folder. LinkedIn is always you, because its terms forbid software acting for a member: a LinkedIn draft row links to the person's LinkedIn page, with the text in the row for you to copy. Not yet: registering for a site or event for you is not offered; a one-click copy of only the message text comes in a later release (the row's Copy copies a prompt naming the draft); the approved send has not yet been tried end to end in a live session, and finding a sent message in a real mailbox is first seen on your own first use, so look in your Sent folder the first time. Quit and reopen Claude after updating.

## jobsearch 0.90.0
When the in-app browser cannot show a page, the job-posting reads, the LinkedIn sweep, the board sweeper and the opportunity researcher now fall back instead of giving up: first to the Chrome extension, then to a scripted fetch of the posting, and only then a loud NOT CHECKED that names what was tried. An unattended run never waits on the extension: it records that the extension was not tried. Reads also wait for the posting text to appear before judging a page, so a page still loading is no longer taken for an empty one. The scripted posting fetch is now automatic for everyone, inside a sandbox admission check: it runs only where your settings keep the sandbox network allowlist in force, and is withheld, with the reason shown in the run summary, where they do not. An explicit posting_fetch.py --set off still wins and stops it everywhere. A notice row in your asks list discloses this, once; on update a migration adds it, and a new profile starts with it. The migration also raises your profile minimum engine to 0.90.0, so an older install on another machine will refuse the new evidence instead of misreading it; update that install before it next runs. The run summary gains a BROWSER FALLBACK line, a READY CHECK line and, for a code it cannot read, UNPARSEABLE. No sandbox setting of yours is changed. Quit and reopen Claude after updating.

## jobsearch 0.88.0
A role is removed only when the pay evidence is certain, outreach you owe is now a plan on the dashboard, and a run that died names what it left. Pay screen: a base pay range that sits below a floor you stated as total pay is no longer removed. The bonus is not stated, so the total could clear the floor: the role is kept for review (PAY-UNCOMPARABLE) and the screen says to ask what the total is. A total-pay range below a base floor is still removed, and a floor whose basis cannot be read is kept for review, never guessed. Each floor's basis is read from its tier, and the comp-tier printout now names it (base or total) instead of calling every floor base. "No pay shown": it is recorded only when the whole description was read and no pay was found, or when you say so yourself. A reader that did not find pay now records it as not captured, and the role is re-read before it is surfaced. A fetched page that states a pay range refuses "none" and names the phrase it found. A board sweep's "pay none" from a minimal capture stores nothing. Follow-ups owed: an application's owed follow-up now clears on any human contact on or after the application date: a sent touch on the role, or a message to or from a person involved in it, or a linked draft. With no contact it expires after network.owed_followup_days (30 by default), and the expiry is said once, by the first run that completes after it. Dashboard: Drafts lists drafts only (ready, held, queued), with no "no draft yet" rows. The Network section is a communication plan: one row per person or role needing a next step, with who, why, last touch and a suggested next step, grouped as applications with no human contact yet, awaiting a reply, referral handoffs and recruiter relationships due this week. A weekly Targets to review list (10 by default, network.targets_per_week) asks yes, no or later for each company, and counts the rest. Aggregators and staffing firms are never targets. No command lines appear on the page: every action is plain words or a copy-as-prompt block that you paste to the coordinator. The dashboard coverage check now compares the Opportunities-to-pursue count with the number of ready roles the pipeline reports. Died runs: a run that started and never ended is called dead only after a window of silence (8 hours by default, runs.liveness_hours, never under 6). Until then it counts as still running. A dead run is named with the files it committed while it ran, and the files it left uncommitted are named only on the machine that ran it. One migration runs by itself on first use: it saves a copy of your opportunities file (opportunities.jsonl.pre-0.88.0), moves each older "none shown" read from listing text aside into listed_pay_prior, which leaves the role flagged for a re-read, and keeps the old value. Update every machine that shares your profile: after this upgrade a machine still on 0.87.0 or older refuses the profile and writes nothing, so every machine you use must be on 0.88.0. Quit and reopen Claude after updating.

A folder you decided with adopt.py folder <name> source or portfolio is no longer listed as undecided. When the basis moves (for example a fast-forward after a hand fix), decisions about files that still exist and did not change are kept, and every cleared decision is printed by name ("N decision(s) cleared because the basis moved"); a parity result is always cleared, because it measured another tree. Only the unknown-key part of the report about piece front matter is fixed here; the rest of it is in 0.4.0. The publish check no longer flags OFL.txt, LICENSE* or *.license as published but not referenced when the same folder holds a .woff2, .woff, .ttf or .otf font; in a folder with no font they are still flagged. The publish guard no longer blocks a command that is not a publish because a here-document body (a commit message passed with <<'EOF') holds an apostrophe or mentions deploy.py: heredoc bodies are removed before the command is read, a heredoc fed to a shell (bash <<EOF) is still read as commands, a real publish goes through the same check as before, and a command that names deploy.py and cannot be read is still blocked, with a message that does not tell you to run /site-studio:publish. One case is not matched: a publish written inside python3 - <<EOF. The content model now ships with the plugin at reference/content-model.md, generated from the build's own tables, and the build's unknown-token messages name its installed path.
