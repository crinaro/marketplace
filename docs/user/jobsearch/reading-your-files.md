# Reading what the search produces

The search writes files that exist to be read by you — company knowledge, call preps, drafts
awaiting your review, and the dashboard. They are not all the same kind of file, and **they do
not all open in the same tool**: the dashboard is HTML and wants a browser, a rendered resume is a
`.docx` and wants a word processor, and everything else is markdown and wants a markdown viewer.
Open one in the wrong tool and you get something readable
but ugly — raw HTML source, or a wall of `#` and `>` markers where formatting should be.

This page says which file opens where, and walks through every realistic way to get at them.

---

## What there is to read

All paths are inside **your profile directory** (the private folder you created at setup — see
[Your data](your-data.md)).

**Starting with 0.32.0, these files sit inside six phase directories** — `presence/`,
`configure/`, `pipeline/`, `applying/`, `conversations/`, `outreach/` — instead of loose at the
profile root. This happens automatically, the first time you open a session after upgrading; you
do nothing to trigger it. The table below gives the path you'll have once that has happened. If
you open your profile folder and still see the old flat names — `kb/`, `call_preps/`,
`drafts.md`, `cover_letters.md` — your next session hasn't run yet; open one and it moves them for
you before you notice.

| file | what it is | format |
|---|---|---|
| `views/dashboard_artifact.html` | **one of two published pages.** A router section up top (one row per phase, naming the next action and a count), then every phase's own section, reached by an in-page link. **Every record is shown in full in exactly one place; anywhere else it is a one-line reference that links to that place** (since 0.64.0 — see *What is on the one page*, below). Drafts, letters and knowledge files show as title + status + location, not in full, except a pending message's **full text**, which lives on this page's outreach section — the one kind of document the page exists to let you read | HTML |
| `views/dashboard_artifact_url.txt` | the URL of the published dashboard Artifact above — a link, not a page | plain text |
| `views/presence_set.html` | **the other published page**, since 0.39.0 — a review copy of `presence/`: your claim union, one tab per declared resume variant, an open-items tab (drift the engine can detect but not fix on its own), and a rules tab for your own settled decisions. Always published, even with zero declared variants — see below | HTML |
| `views/presence_set_url.txt` | the URL of the published presence-set Artifact above | plain text |
| `presence/rules.md` | **authored by you, not generated** — the settled decisions the rules tab above renders. Created once, seeded with three starting rules, the first time you open a session after upgrading to 0.39.0 | markdown |
| `presence/resumes/*.docx` | **rendered printed resumes** — one file per variant you have asked to be rendered, named `<your-name-slug>_resume_<variant-id>.docx`. Written only when you render one, so a profile that never has does not have this directory at all. Older profiles rendered these to a bare `resumes/` at the profile root — see *Two things that moved out of the profile root*, below | .docx |
| `views/applying.md` | the working queue: roles to apply to, and the follow-up work a submission created. Generated and read-only — never published, regenerated fresh every time you open an application session | markdown |
| `views/conversations.md` | what each upcoming call still needs: whether its prep is written, and if not, that it is **owed**. Generated and read-only, regenerated by the scheduled daily/weekly runs (not only in session) — a `PREP OWED` row is what the search acts on to write the prep before the call | markdown |
| `pipeline/kb/<company>.md` | durable knowledge about one company, e.g. `pipeline/kb/acme-health.md` | markdown |
| `conversations/call_prep_<date>.md` | prep notes for a scheduled call, e.g. `conversations/call_prep_2026-01-15.md`. A note written when full research wasn't available carries `**Prep status:** incomplete — <reason>` under its heading — see below. **Since 0.36.0, a prep for a call already held moves automatically** to `archive/call-preps/` — see *A call prep that has already happened*, below | markdown |
| `outreach/drafts.md` | **since 0.47.0, the working set only** — staged outreach messages still awaiting your review, each carrying a `**Medium:**` line naming how it goes out; see below. A sent or moot entry no longer accumulates here — see *`drafts.md` is a working set, not an archive*, below | markdown |
| `applying/cover_letters.md` | letters, one per role — a letter carrying an unresolved send-hold shows a `**Blocked until:**` marker and is not ready to submit; see below | markdown |

**The dashboard is one page, not a set — a second page has a different purpose.** Earlier versions
had one `dashboard.html` that inlined every draft, letter and kb file in full — it grew to
hundreds of KB and kept a local copy that could silently drift from what was actually published. A
version after that split the page into a router, a state view and a phase page per area, published
separately — which turned out to have its own failure: a phase page could publish once and then,
as its item count changed, silently stop being republished while its old URL kept serving a stale
snapshot forever. Now every draft, letter or knowledge file renders as **title + status +
location** on the one dashboard page, its full body living once on that page's own section, and
the whole page republishes together every run so no section's URL can go stale while another's
stays current. The root `dashboard.html` that the split left behind as a pointer is not part of
this any more — it is retired; see *Two things that moved out of the profile root*, below.

### What is on the one page (since 0.64.0)

The dashboard is still one page at one link. What changed in 0.64.0 is that it now follows one
rule everywhere: **a role, a draft, a channel or a person is shown in full in exactly one list —
its own. Anywhere else it comes up, you get a one-line reference with a link to that row**, never
a second copy that could disagree with the first. Every in-page link on the page lands on
something that is there; the router no longer points at a section the run did not draw.

- **Drafts and Opportunities come first.** Right under the router summary, before every other
  section: the follow-up list (your drafts, in full) and then the opportunities list. A bar pinned to
  the top of the page, **Drafts (N)** and **Opportunities (N)**, jumps to either one from anywhere
  on the page, even while a filter is selected. N is the number of drafts or roles in that list.
- **Opportunities.** One main choice, labelled **Show**, in terms of whose move it is: *Your move
  — today*, *New — pursue or pass?*, *In live conversation*, *Sent — awaiting a reply*, *Not sent
  yet — queued to apply*, *In interviews*, *Parked*, and *Ended* (the cause shows on each row). A second choice, **Whose**,
  splits the list by who owes the next move. Rows are ordered by whose move it is, then by how
  long since anything last happened on the role. The older state, stage and coverage choices are
  gone from this list (the stage still shows on each row). **A choice that would show exactly the
  same rows as *All* is not drawn**, and a group left with only *All* is not drawn at all — so on a
  small search you see fewer buttons, not buttons that do nothing.
- **The router's "applying" count is a button.** Click the **number** and the opportunities list
  narrows to *Not sent yet — queued to apply*; click the **phase name** to jump down to the list.
  The separate "applying queue" and "decide" sections are gone — the same roles are the
  *Not sent yet* and *New* choices on the one list.
- **Follow-ups — what to send** is one list. Drafts you have staged are shown with their full
  text, as before. A relationship touch that is due, an application with no follow-up drafted, and a
  person who is due each appear as a short reference row ("no draft yet — <why>") that links to the
  channel, role or person it is about. The **When** choice opens on *Now* — drafts you can send or
  must unblock, plus anything due in the next **5 days** — with *Waiting* and *Later* one click
  away; **Ready to send** is a choice under **Sendability**. The three older follow-up sections
  (ready, touches, sequences) are gone; their rows are in this list. **People due** is unchanged
  and still the one place a person is listed in full.
- **Channels — due.** Only channels with a review or a touch due are shown as rows. Every other
  channel is one counted line — *N other channels: K current, R retired. Nothing due* — that names
  the file, `data/channels.jsonl`, where they live. Ask the session *"show my channels"* for the
  full table. The old reviews and sourcing tables are gone; no channel was dropped, they are
  counted instead of listed.

The page republishes whole every run, and a check run with it reads your files and the page
together and fails if a record appears in full twice, a reference points at nothing, or a link on
the page has no destination.

### Triaging versus Decide (since 0.67.0)

A newly sourced role used to count as a pursue-or-pass decision the moment it was captured, whether
or not anyone had read the posting. Now a role reaches **Decide** (the page's group *Decide —
pursue/pass owed*) only after the system has done its reading. Until then it sits in its own group,
**Triaging — the system is reading these**, and it is *not* on your list: nothing in that group is
waiting on you. Both are groups you can select on the page, beside *Your move — today*. A role is in
*Triaging* **or** in *New — pursue or pass?*, never both: *New* lists the undecided roles that have
been read, and its count leaves out the roles still being read, which appear only under *Triaging*
(each still shows once on the page). *Decide* is the decisions owed, and sits inside *New* (a role
shown unread by the stuck rule below counts in both). When roles are being read, the line at the top
of the page says how many.

A role leaves Triaging for Decide when the record has all of: the job description was read (with
where it was read from), the pay as the listing wrote it, the work setting as the listing wrote it,
the hard screens applied, and a **lean**. A role the screen removes never reaches Decide at all.

- **A lean** is the system's read of a role: `pursue`, `pass` or `ask`, plus one line. It is
  shown on the role's card in Decide as advice. **A lean never removes a role and never decides
  for you**; only the hard rules (a stated range below your floor, a place you have ruled out) remove.
- **Likely-pass signals** are phrases you can list in your settings
  ([`screen.likely_pass_signals`](your-data.md#screening--configjsonscreen)), each with a reason. When a role's title, job
  description or company matches one, its card shows a **LEAN** line with your reason. It is
  a reason to look closely, nothing more.
- **A recruiter role that is old or of unknown age defaults to `ask`.** When the screen's age line
  asks for a first move (a role from a recruiter channel older than `search.retained_search_age_days`,
  or with no known age), its lean is `ask` and the line is that first move: "FIRST MOVE: ask the
  recruiter what stage the search is in, before research or letters" (or, for an unknown age, "ask
  the recruiter when the search opened"). The run states a different lean only when the job
  description gives a reason, and says so in the line.
- **A read that failed still ends.** If the job description could not be read (a login wall, a dead
  link, no link at all, or a surface with no browser), the role goes to Decide with the lean `ask`
  and the line "not read: <reason>", so you are never left waiting on a read that cannot happen.
- **Nothing waits forever.** A role still in Triaging once `search.triage_stuck_days` days have
  passed (default 3, counted from its first sighting) is shown to you in Decide anyway, labelled
  "not yet read (waited K days)", with the lean `ask`. A role with no readable sighting date has
  no age to wait out, so it is shown at once, labelled "not yet read (age unknown)". Each daily
  run triages at most `search.triage_per_run` roles (default 10, oldest first sighting first) and
  prints one line, for example `triaging: 4 waiting, 6 triaged this run, 0 over the stuck bound`:
  how many are still being read, how many this run finished, and how many are past the stuck
  limit and so reached you unread.
- **A title below your floor leans by pay, and is never removed (since 0.69.0).** If you set
  [`screen.title_floor`](your-data.md#screening--configjsonscreen) and a role's title reads below
  it, the card in Decide shows a computed lean: **pursue**, "title below your floor (<floor>), but
  pay is within your range", when the listed pay clears your floor; **ask**, "title below your
  floor (<floor>); check pay before deciding", when pay is not known or cannot be compared. When the
  pay itself is below your floor the pay rule has already removed the role and the title adds
  nothing. Phrases you list for the title field of `screen.likely_pass_signals` (the mandate) show
  as a **LEAN to pass** with your reason, titled `OFF-MANDATE`. In both cases the role stays on the
  page for you to decide.
- **A job description only a browser can read waits for a browser session (since 0.69.0).** If the
  posting needs a signed-in browser and this run has none, the role stays in Triaging and a
  `read-jd` item is queued for a session that does. You will see it under *needs another
  environment* in `deferred.py --claimable`. Once it has waited past `search.triage_stuck_days` the
  role goes to Decide with the lean `ask` and the line "not read: surface-cannot-read".
- **Decide is the decisions part of the needs-you filter.** *Your move — today* (the needs-you
  filter) shows the decisions owed plus the actions due today, and its caption says so: "decisions
  owed plus actions due today". *Decide — pursue/pass owed* is exactly the decisions owed. Both
  come from one definition, so their counts cannot drift apart. Triaging is in neither.

**On upgrade:** every role that was waiting on your pursue-or-pass and has not been read shows as
Triaging, and drains into Decide over the next daily runs.

### A sweep that was held, and the counts under it (since 0.69.0)

When a LinkedIn or board sweep reports that its page was not showing what was asked (a filter
dropped, a parameter you never set, an unapplied date window, a cut-short list), the roles that only
those queries showed are **held** instead of captured. You see it in three places:

- **The run summary's roles line** gains the count and the reasons, for example `... · 2 quarantined
  (filter-dropped ×1, truncated ×1)`.
- **A second line says how each query read**, for example `query reads (board): 12 reached · 10
  clean · 1 filters unread · 1 degraded (truncated ×1) · 2 total unknown`. *Filters unread* and
  *total unknown* mean the sweep could not tell; those are counted and never hold a role. A run
  from before 0.69.0 prints no such line, which is not the same as reaching nothing.
- **`deferred.py --claimable`** lists held items under *QUARANTINED*. The pass's own output
  (`deferred.py --add-roles`) prints `QUARANTINED <url> (q=…: <reasons>)` per held role and a closing
  `HELD N role(s) (quarantined) from degraded queries: …` line.

**How a held role is released.** A later sweep that sees it through a clean query releases it
automatically (the line reads `RELEASED`), and it is then captured like any other. Or release it
yourself: `~/.claude/jobsearch/run deferred.py --unquarantine <item id>`. Nothing is dropped or
deleted while it is held.

**The all-clean flag.** `check_runs.py` prints `BOARD SWEEP READS ALL-CLEAN` when the last 7 board
passes in a row each reported every reached query clean. These are the sweep's own reports of what a
page showed, and nothing here can verify them. A sweep that never looks at the page would report
exactly that pattern, so the flag asks you to open one board's results page and compare it with its
query line before trusting the streak. It is advice, and nothing is blocked.

### A role's place, a flag on it, and a folded row (since 0.70.0)

Three things in `opportunities.jsonl` and in the screen's printed lines are new, and each is there to
say how a place was known.

- **`inferred` on a role's location.** Some postings state no work setting. When one gives a
  concrete place anyway (a line such as `Riverton, ST`), the role is recorded as `onsite` with
  `location.setting_source: inferred`, and the screen line for it ends *(onsite inferred: the posting
  stated no setting)*. Read it as "assumed onsite from the place", not "the posting said onsite". The
  assumption is safe to act on only because a role far enough away is as impractical hybrid as onsite.
  If you correct the setting, the role keeps a record of the correction
  (`location.inference_overturned`, with what it was, what it became and the date) and the flag goes.
  A role with no setting and no readable place has no `type` at all and is kept for review.
- **`duplicate_of` on a row.** When one requisition was recorded twice, the duplicate row can be folded
  into the one that stands for the role with `record.py link-sibling <duplicate> --into <kept row>`. The folded row names
  the kept one in `duplicate_of`, its listings move onto the kept row as sightings, and it drops out of
  the undecided list and out of matching. Nothing is deleted, so it is still there to read. A screen
  of a not-yet-folded second listing prints `DUPLICATE of <row>` on its *passed* line and repeats the
  kept row's verdict.
- **`location` on a sighting.** Each sighting may say where that listing placed the role, so a role
  listed in several cities shows every place it was seen. The role is screened at its most favourable
  place. A sighting marked `split_to` was moved to another row when a wrong merge was undone, and no
  longer counts for this one.

The summary line printed after several roles are screened looks like this, with made-up numbers:
`MINIMAL SCREEN SUMMARY 12 screened · keep 5 · remove 4 (geo 3, comp 1, passed 0) · review 3 ·
commute: outside 3, near 2, unresolvable 1`. A role counted *outside* was removed as too far from
every commute anchor; *near* needs a commute estimate from you; *unresolvable* means the place text
could not be read as a place. If the shipped place table is missing you will see `PLACE TABLE MISSING
... distance not checked`, which means no distance was measured at all. How the distance is worked out
is in [Your data](your-data.md#where-a-role-is-and-when-it-is-too-far--since-0700).

### Correcting a draft from a comment on the page (since 0.64.0)

If your published dashboard is shared inside your organization on claude.ai, a reviewer can leave
a comment on it — say, that one phrase in a draft should read differently. **The search never
fixes that by editing the page**, because the page is regenerated from your files and an edit to
it would be lost on the next run. Instead, in a session, the coordinator reads the comment and
turns it into a correction to the draft in `outreach/drafts.md`:

1. It shows you a **before and after** of that draft and writes nothing yet.
2. It applies the change only after you say yes, and only if the text being replaced occurs
   **exactly once** in that draft — a phrase that appears twice, or not at all, is refused.
3. It records the change on the draft as a `**Revised:**` line (date, where the comment came
   from, old text, new text) — see *A line you may see in `outreach/drafts.md`: `**Revised:**`*, below.
4. It regenerates and republishes the page.

Applying the same correction twice is refused, not repeated. A comment it cannot apply is left
open and the session tells you why; it is never marked resolved.

**What this needs.** Claude Code version 2.1.221 or later, a session you are in (not a scheduled
run), and a dashboard shared within an organization — comments do not exist on a private
artifact or a bare public link. **Where any of that is missing, paste the correction into the
session instead** (*"in the Corvid Labs draft, change 'next week' to 'this month'"*) and it goes
through the same before-and-after and the same yes.

**Or use the Copy as prompt button.** Each draft on the dashboard has a **Copy as prompt** button.
It copies a short block that names that exact draft, even when two drafts share a title, and quotes
its current text. Paste it into your session, replace `<describe the change here>` with what
should change, and send it. If your browser blocks copying, the block appears selected under the
button; press Cmd+C (Mac) or Ctrl+C. The button only copies text; nothing is sent from the page.

**`views/presence_set.html` (since 0.39.0) is not that same kind of split reopened.** It exists so
you can review what `presence/` actually looks like rendered — the claim union, every declared
variant, your own rules — instead of only reading its markdown sources. Unlike the phase pages
that failed above, it does not depend on your data: it publishes on a profile with zero declared
variants exactly as it does on five, so it is never at risk of quietly going stale by falling
below some threshold.

### Two things that moved out of the profile root

Two files an earlier version of this page told you to look for at the profile root are not there
any more. **Neither move deletes anything**, and both happen on their own, the first time you open
a session after upgrading — you do nothing to trigger them.

- **`dashboard.html` is gone from the root, and stays gone.** It was a tombstone stub — a note
  saying the dashboard had moved — and it was rewritten on every single run, so deleting it never
  worked. The generator no longer writes it, and the upgrade **moves** an existing one to
  `archive/retired-trackers/dashboard.html`. That is true even if the file at that path was
  something you wrote yourself: it moves, unchanged, rather than being deleted. If a file of that
  name is already at the destination, your root copy is **left where it is** and named in the
  upgrade's summary, never overwritten. The dashboard itself is `views/dashboard_artifact.html`,
  and the published page's URL lives in `views/dashboard_artifact_url.txt` — that file is the one
  place to look for the link.
- **Rendered resumes moved from a root `resumes/` into `presence/resumes/`.** The old default put
  them at the profile root, which the engine's own layout audit treats as a place only anchor files
  belong, so rendering a resume made the profile fail that audit. The upgrade moves the files into
  `presence/resumes/`, contents intact; a name already present at the destination is left at the
  root and named rather than clobbered (a rendered resume may be a document you have already
  sent), and a root `resumes/` left empty afterwards is removed. If you had already set your own
  output directory in `config.json`, it is untouched — only the default changed. A profile the
  upgrade has not reached yet keeps reading and writing the old location, so nothing breaks while
  it is pending.

### A marker you may see under a call prep's heading

A prep note written when full research wasn't available (a scan failed, a source was
unreachable) is not skipped — it's written as far as it could go, with a line under its heading:

```
**Prep status:** incomplete — <reason>
```

`views/conversations.md` treats that call's prep as **still owed**, the same as if nothing had
been written at all, so it stays on your radar rather than looking finished. The next capable run
finishes the note in place — never a second file. If you see this marker on a note you're about to
read before a call, treat it as a heads-up that the note may be missing something, not as an
error.

### A call prep that has already happened

Since 0.36.0, a prep dated before today moves out of `conversations/` and into
`archive/call-preps/` on its own, every run — you do not need to remember to archive it, and
nothing you do triggers it. If durable content from the call was never promoted into
`pipeline/kb/<company>.md` before that happened, the archived note gets a `**Promoted:**
unresolved` line appended so the gap stays visible rather than quietly moving out of sight with
the file.

The dashboard only renders a prep **in full** when its call is within the next 7 days. A prep for
a call further out, one already archived, or one with no date at all still appears — as a row
under *"Other call preps — index only"* naming the file, not its content. Open the file itself
for those.

The datasets (`data/*.jsonl`) are deliberately not in this table — they are for querying, not
reading, and [Your data](your-data.md) covers them. Neither is `.jobsearch/`, a folder you will
also see in your profile: it holds engine diagnostics, not anything about your search, and
[Your data](your-data.md#jobsearch-engine-state-not-your-data) explains what it is.

### `drafts.md` is a working set, not an archive (since 0.47.0)

A sent or moot entry used to just stay in `outreach/drafts.md` forever, under its own
`**Status:**` line. As of 0.47.0 it does not: `precondition.py --prune` removes every terminal
(`SENT` or `MOOT / DO-NOT-SEND`) entry from the file, and the fact it recorded goes somewhere
durable instead — never dropped. Where the entry named a role, its paragraph becomes a
`research_log[]` row on that opportunity (`data/opportunities.jsonl`); where it addressed only a
channel-anchored person with no role, it becomes a `log[]` row on that channel
(`data/channels.jsonl`) instead. If a matching send was already recorded elsewhere (an
`outreach`/`messages` row for the same touch), the draft's paragraph is simply removed rather
than relocated a second time. An entry naming neither a role nor a channel-resolvable contact is
left in place, reported rather than guessed at.

The block of text above your first entry is also no longer something you or an earlier session
wrote — it is **generated** by `precondition.py --format`, marked by an HTML comment, and
regenerated rather than hand-edited when it needs to change.

The 0.47.0 upgrade runs this relocation once, automatically, so your existing `drafts.md` starts
this release already holding only what is genuinely still under review.

## A line you may see in `outreach/drafts.md`

Every draft entry carries a `**Medium:**` line directly under its `**Status:**` line:

```
**Status:** DRAFT
**Medium:** linkedin-message
```

This is not decoration — it is what the dashboard reads to know how the message is meant to go
out (a LinkedIn note, a cold email, a reply in an existing thread, and so on), and it is what its
per-medium counts and filters are built from. From 0.37.0, **the search writes this line for
you** whenever it drafts or changes a message's medium — you should not normally need to touch it
yourself.

**Starting with 0.37.0, upgrading may add or move this line on drafts that predate it.** Earlier
drafts sometimes had the medium named only inside the `**Status:**` line's own text (something
like `**Status:** rewritten shorter. **Medium: linkedin-message** (~40 words, cap 40)`) — a shape
the dashboard's reader was never able to see, so those rows rendered as `medium: unknown` even
though the right value was sitting right there. Where that exact shape exists — one clear,
recognised value, named once, inside the Status line, and no `**Medium:**` line already present —
the upgrade moves it onto its own line automatically, once, and leaves the `**Status:**` line
otherwise untouched.

**What `medium: unknown` on a row means, and what to do about it:** the entry has no `**Medium:**`
line the dashboard can read — either none was ever written, or the medium is named somewhere the
migration could not safely relocate on its own (two mentions, an unrecognised term, or buried
inside other prose). Add or fix the line yourself, directly under `**Status:**`, in the exact
form `**Medium:** <value>` — one of: `linkedin-connection-note`, `linkedin-inmail`,
`linkedin-message`, `email-cold`, `email-reply`, `phone`, `sms`, `other`. Nothing is lost if you
leave it as `unknown` — the draft still sends the same — but the dashboard's medium counts and
filters will undercount it until the line is there.

## A line you may see in `outreach/drafts.md`: `**Revised:**`

When a correction is applied to a draft (see *Correcting a draft from a comment*, above), the
draft gains one line recording it:

```
**Revised:** 2026-10-14 · comment:t-4821 · "next week" → "this month"
```

It is a note about the edit, not part of the message: it is never sent, and it does not change
whether the draft counts as ready, held or sent. (If recording a correction would change that —
for example, removing a phrase that was holding the draft would leave the old phrase quoted on this
line — the step refuses and says so, rather than leave the draft blocked.) The source reads `chat` when the correction came
from you in the session rather than from a comment. Nothing needs doing about it; delete the line
if you do not want the record.

## A marker you may see in `applying/cover_letters.md`

Upgrading to 0.27.0 may add a line under a letter's heading that was not there before:

```
**Blocked until:** unresolved (migrated 0.27.0 from prose)
```

That is not new information. It is a hold that already existed in the letter's own prose — a note
like "wait until they confirm the licensing question" — made structured, so the dashboard can act
on it instead of only a person reading the text. `unresolved` means the hold is real but not yet
machine-checkable: nothing has said **what** it is waiting on.

**What this means for you:** a letter carrying an unmet `**Blocked until:**` line — `unresolved` or
anything else not satisfied yet — renders on the dashboard as a **"Held"** row in the one
cover-letters list (filtered by sendability), with no inline body, not in the ready rows, even if
you consider the letter itself finished. To clear it:

- replace `unresolved` with the real condition once you know it —
  `**Blocked until:** contact:<id> outcome:<accepted|replied|...>` — and the letter moves to ready
  by itself the next time the dashboard is generated, or
- delete the `**Blocked until:**` line if the letter was never actually held.

The original prose that prompted the marker is left in place beneath it — nothing was deleted, only
made visible to the dashboard as well as to you.

## Which file opens in which tool

This is the part nothing else tells you, so here it is as a table:

| you want to read | open it in | in the wrong tool you get |
|---|---|---|
| the dashboard (router + every phase, on one page), or the presence review page (`views/presence_set.html`) | a **web browser** — double-click the local `.html` file, or open its published Artifact link | a text editor shows thousands of lines of raw HTML |
| the working queue (`views/applying.md`), what's owed for upcoming calls (`views/conversations.md`), a call prep, kb file, `outreach/drafts.md`, `applying/cover_letters.md` | a **markdown-rendering viewer** — the desktop app, or an editor with markdown preview | a browser or plain editor shows the unrendered source: readable, but the structure that makes it scannable is gone |
| a rendered resume (`presence/resumes/*.docx`) | a **word processor** — Word, Pages, LibreOffice, or Google Docs after an upload | a plain text editor shows a binary file, not a document |
| an Artifact URL | it is just a link — open the file, copy the URL into any browser on any device | — |

Rule of thumb: **`.html` means browser, `.md` means markdown viewer, `.docx` means word
processor.**

## The routes, cleanest first

### 1. The desktop app's `</>` Code side — recommended

Open the Claude Code side of the desktop app in your profile directory and ask for what you
want: *"show me the call prep for tomorrow"*, *"what is in the kb file for Acme Health?"*,
*"read me the pending drafts."* The session finds the file, renders the markdown properly, and
can answer questions about it — which no file manager can. This is the cleanest route because
it is the same place the search already runs, and it needs no extra tooling.

For the dashboard, ask the session to open `views/dashboard_artifact.html` in your browser, or
use route 2. For the presence review page, `views/presence_set.html`.

### 2. The published Artifacts — best on a phone

Every daily run republishes **two** claude.ai Artifacts, each at its own **stable URL**: the
dashboard (`views/dashboard_artifact_url.txt`) and the presence review page
(`views/presence_set_url.txt`, since 0.39.0). Open the dashboard — the router section up top
names the next action and a count per phase, and each phase name is a link down to its own
section on the same page (a count that is a filter, like *applying*, narrows the list when you
click the number). This is the one route that needs neither the desktop app nor the local
folder, which makes it the practical way to check state from a phone. **A pending message's full
text lives on this page's outreach section** — drafts and cover letters show as title + status +
location everywhere else, and kb files render as content on their own sections too. A call prep
renders in full only when its call is within the next 7 days; a further-out, already-archived, or
undated prep is an index row under *"Other call preps — index only"* instead.

The presence review page is separate: one tab per declared resume variant, a claim-union tab, an
open-items tab, and a rules tab — it exists to let you see what `presence/` actually looks like
rendered, not to route your day, and it publishes every run whether or not you have declared any
variants.

Both Artifacts are **default-private** to your claude.ai account. Each shows what the last run
published; for state newer than the last run, use routes 1 or 3. `views/applying.md` (the working
queue) and `views/conversations.md` (what's owed for upcoming calls) are never published this way;
see route 1 or 3 for them.

### 3. The local folder, with a markdown-capable editor

Everything is a plain file, so any editor opens it — but for the markdown to *render* you want
an editor with a markdown preview. VS Code is the common choice: open your profile folder,
select a `.md` file, and toggle preview with **Cmd+Shift+V** (macOS) or **Ctrl+Shift+V**
(Windows/Linux). Any dedicated markdown viewer works the same way. Without a preview you get
the raw source — every fact is there, the scannability is not.

### 4. The browser, for the HTML only

Double-click `views/dashboard_artifact.html` and it opens in your default browser, fully rendered,
no server needed — this is the freshest view after a run finishes locally, since this local file
is generated in the same step as the published copy. There is no longer an `.html` file at the
profile root to double-click by mistake — the `dashboard.html` stub that used to sit there is
retired (see *Two things that moved out of the profile root*). Do **not** open the
`.md` files this way — a browser does not render markdown, so a call prep (or
`views/applying.md`, or `views/conversations.md`) becomes a single run-on wall of text.

### 5. Your profile's private git remote, if you have one

If you followed the backup recommendation and your profile syncs to a **private** git
repository, the hosting site's web view renders markdown files properly — which quietly gives
you a phone-friendly reader for kb files and call preps too, at whatever freshness your last
push was. This route is only as private as that repository; keep it private.

## The morning-of-an-interview case

A call prep exists precisely because something is scheduled soon, so the fast paths matter:

- **At a computer:** route 1 — ask the session for the prep by date or company.
- **On a phone:** route 2 — the conversations section of the dashboard renders the prep as content
  when the call is within the next 7 days (the usual case for "an interview is coming up"); a
  further-out or already-archived prep is an index row there, so open the file itself instead (see
  *A call prep that has already happened*, above).
- **No Claude available at all:** route 3 or 5 — the file itself, in anything that shows
  markdown.

## What this page is not

It does not decide which of these routes is *supported* — they all are; the plugin's files are
plain HTML and markdown exactly so that no single tool owns them. It also does not cover
editing: for changing files by hand and validating afterwards, see
