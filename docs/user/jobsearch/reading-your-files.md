# Reading what the search produces

The search writes files that exist to be read by you — company knowledge, call preps, drafts
awaiting your review, and the dashboard. They are not all the same kind of file, and **they do
not all open in the same tool**: the dashboard is HTML and wants a browser, everything else is
markdown and wants a markdown viewer. Open one in the wrong tool and you get something readable
but ugly — raw HTML source, or a wall of `#` and `>` markers where formatting should be.

This page says which file opens where, and walks through every realistic way to get at them.

---

## What there is to read

All paths are inside **your profile directory** (the private folder you created at setup — see
[Your data](your-data.md)).

**Starting with 0.32.0, these files sit inside six phase directories** — `presence/`,
`configure/`, `pipeline/`, `applying/`, `conversations/`, `outreach/` — instead of loose at the
profile root. This happens automatically, the first time you open a session after upgrading; you
do nothing to trigger it. The table below gives the path you'll have once that has happened. If
you open your profile folder and still see the old flat names — `kb/`, `call_preps/`,
`drafts.md`, `cover_letters.md` — your next session hasn't run yet; open one and it moves them for
you before you notice.

| file | what it is | format |
|---|---|---|
| `dashboard.html` | a **tombstone stub** — a note saying the dashboard moved, nothing else. Kept only so double-clicking the old filename tells you where things went | HTML |
| `views/dashboard_artifact.html` | **the published page — the only one.** A router section up top (one row per phase, naming the next action and a count), then every phase's own section, reached by an in-page link. Drafts, letters and knowledge files show as title + status + location, not in full, except a pending message's **full text**, which lives on this page's outreach section — the one kind of document the page exists to let you read | HTML |
| `views/dashboard_artifact_url.txt` | the URL of the published Artifact above — a link, not a page | plain text |
| `views/applying.md` | the working queue: roles to apply to, and the follow-up work a submission created. Generated and read-only — never published, regenerated fresh every time you open an application session | markdown |
| `views/conversations.md` | what each upcoming call still needs: whether its prep is written, and if not, that it is **owed**. Generated and read-only, regenerated by the scheduled daily/weekly runs (not only in session) — a `PREP OWED` row is what the search acts on to write the prep before the call | markdown |
| `pipeline/kb/<company>.md` | durable knowledge about one company, e.g. `pipeline/kb/acme-health.md` | markdown |
| `conversations/call_prep_<date>.md` | prep notes for a scheduled call, e.g. `conversations/call_prep_2026-01-15.md`. A note written when full research wasn't available carries `**Prep status:** incomplete — <reason>` under its heading — see below. **Since 0.36.0, a prep for a call already held moves automatically** to `archive/call-preps/` — see *A call prep that has already happened*, below | markdown |
| `outreach/drafts.md` | staged outreach messages awaiting your review — each carries a `**Medium:**` line naming how it goes out; see below | markdown |
| `applying/cover_letters.md` | letters, one per role — a letter carrying an unresolved send-hold shows a `**Blocked until:**` marker and is not ready to submit; see below | markdown |

**The published surface is one page, not a set.** Earlier versions had one `dashboard.html` that
inlined every draft, letter and kb file in full — it grew to hundreds of KB and kept a local copy
that could silently drift from what was actually published. A version after that split the page
into a router, a state view and a phase page per area, published separately — which turned out to
have its own failure: a phase page could publish once and then, as its item count changed,
silently stop being republished while its old URL kept serving a stale snapshot forever. Now every
draft, letter or knowledge file renders as **title + status + location** on the one page, its full
body living once on that page's own section, and the whole page republishes together every run so
no section's URL can go stale while another's stays current. `dashboard.html` itself carries no
state at all.

### A marker you may see under a call prep's heading

A prep note written when full research wasn't available (a scan failed, a source was
unreachable) is not skipped — it's written as far as it could go, with a line under its heading:

```
**Prep status:** incomplete — <reason>
```

`views/conversations.md` treats that call's prep as **still owed**, the same as if nothing had
been written at all, so it stays on your radar rather than looking finished. The next capable run
finishes the note in place — never a second file. If you see this marker on a note you're about to
read before a call, treat it as a heads-up that the note may be missing something, not as an
error.

### A call prep that has already happened

Since 0.36.0, a prep dated before today moves out of `conversations/` and into
`archive/call-preps/` on its own, every run — you do not need to remember to archive it, and
nothing you do triggers it. If durable content from the call was never promoted into
`pipeline/kb/<company>.md` before that happened, the archived note gets a `**Promoted:**
unresolved` line appended so the gap stays visible rather than quietly moving out of sight with
the file.

The dashboard only renders a prep **in full** when its call is within the next 7 days. A prep for
a call further out, one already archived, or one with no date at all still appears — as a row
under *"Other call preps — index only"* naming the file, not its content. Open the file itself
for those.

The datasets (`data/*.jsonl`) are deliberately not in this table — they are for querying, not
reading, and [Your data](your-data.md) covers them. Neither is `.jobsearch/`, a folder you will
also see in your profile: it holds engine diagnostics, not anything about your search, and
[Your data](your-data.md#jobsearch-engine-state-not-your-data) explains what it is.

## A line you may see in `outreach/drafts.md`

Every draft entry carries a `**Medium:**` line directly under its `**Status:**` line:

```
**Status:** DRAFT
**Medium:** linkedin-message
```

This is not decoration — it is what the dashboard reads to know how the message is meant to go
out (a LinkedIn note, a cold email, a reply in an existing thread, and so on), and it is what its
per-medium counts and filters are built from. From 0.37.0, **the search writes this line for
you** whenever it drafts or changes a message's medium — you should not normally need to touch it
yourself.

**Starting with 0.37.0, upgrading may add or move this line on drafts that predate it.** Earlier
drafts sometimes had the medium named only inside the `**Status:**` line's own text (something
like `**Status:** rewritten shorter. **Medium: linkedin-message** (~40 words, cap 40)`) — a shape
the dashboard's reader was never able to see, so those rows rendered as `medium: unknown` even
though the right value was sitting right there. Where that exact shape exists — one clear,
recognised value, named once, inside the Status line, and no `**Medium:**` line already present —
the upgrade moves it onto its own line automatically, once, and leaves the `**Status:**` line
otherwise untouched.

**What `medium: unknown` on a row means, and what to do about it:** the entry has no `**Medium:**`
line the dashboard can read — either none was ever written, or the medium is named somewhere the
migration could not safely relocate on its own (two mentions, an unrecognised term, or buried
inside other prose). Add or fix the line yourself, directly under `**Status:**`, in the exact
form `**Medium:** <value>` — one of: `linkedin-connection-note`, `linkedin-inmail`,
`linkedin-message`, `email-cold`, `email-reply`, `phone`, `sms`, `other`. Nothing is lost if you
leave it as `unknown` — the draft still sends the same — but the dashboard's medium counts and
filters will undercount it until the line is there.

## A marker you may see in `applying/cover_letters.md`

Upgrading to 0.27.0 may add a line under a letter's heading that was not there before:

```
**Blocked until:** unresolved (migrated 0.27.0 from prose)
```

That is not new information. It is a hold that already existed in the letter's own prose — a note
like "wait until they confirm the licensing question" — made structured, so the dashboard can act
on it instead of only a person reading the text. `unresolved` means the hold is real but not yet
machine-checkable: nothing has said **what** it is waiting on.

**What this means for you:** a letter carrying an unmet `**Blocked until:**` line — `unresolved` or
anything else not satisfied yet — renders on the dashboard as a **"Held"** row in the one
cover-letters list (filtered by sendability), with no inline body, not in the ready rows, even if
you consider the letter itself finished. To clear it:

- replace `unresolved` with the real condition once you know it —
  `**Blocked until:** contact:<id> outcome:<accepted|replied|...>` — and the letter moves to ready
  by itself the next time the dashboard is generated, or
- delete the `**Blocked until:**` line if the letter was never actually held.

The original prose that prompted the marker is left in place beneath it — nothing was deleted, only
made visible to the dashboard as well as to you.

## Which file opens in which tool

This is the part nothing else tells you, so here it is as a table:

| you want to read | open it in | in the wrong tool you get |
|---|---|---|
| the dashboard (router + every phase, on one page) | a **web browser** — double-click the local `.html` file, or open its published Artifact link | a text editor shows thousands of lines of raw HTML |
| the working queue (`views/applying.md`), what's owed for upcoming calls (`views/conversations.md`), a call prep, kb file, `outreach/drafts.md`, `applying/cover_letters.md` | a **markdown-rendering viewer** — the desktop app, or an editor with markdown preview | a browser or plain editor shows the unrendered source: readable, but the structure that makes it scannable is gone |
| an Artifact URL | it is just a link — open the file, copy the URL into any browser on any device | — |

Rule of thumb: **`.html` means browser, `.md` means markdown viewer.**

## The routes, cleanest first

### 1. The desktop app's `</>` Code side — recommended

Open the Claude Code side of the desktop app in your profile directory and ask for what you
want: *"show me the call prep for tomorrow"*, *"what is in the kb file for Acme Health?"*,
*"read me the pending drafts."* The session finds the file, renders the markdown properly, and
can answer questions about it — which no file manager can. This is the cleanest route because
it is the same place the search already runs, and it needs no extra tooling.

For the dashboard, ask the session to open `views/dashboard_artifact.html` in your browser, or
use route 2.

### 2. The published Artifact — best on a phone

Every daily run republishes the dashboard as **one** claude.ai Artifact at a **stable URL**
(`views/dashboard_artifact_url.txt`). Open it — the router section up top names the next action
and a count per phase, and each phase name is a link down to its own section on the same page.
This is the one route that needs neither the desktop app nor the local folder, which makes it the
practical way to check state from a phone. **A pending message's full text lives on this page's
outreach section** — drafts and cover letters show as title + status + location everywhere else,
and kb files render as content on their own sections too. A call prep renders in full only when
its call is within the next 7 days; a further-out, already-archived, or undated prep is an index
row under *"Other call preps — index only"* instead.

This Artifact is **default-private** to your claude.ai account. It shows what the last run
published; for state newer than the last run, use routes 1 or 3. `views/applying.md` (the working
queue) and `views/conversations.md` (what's owed for upcoming calls) are never published this way;
see route 1 or 3 for them.

### 3. The local folder, with a markdown-capable editor

Everything is a plain file, so any editor opens it — but for the markdown to *render* you want
an editor with a markdown preview. VS Code is the common choice: open your profile folder,
select a `.md` file, and toggle preview with **Cmd+Shift+V** (macOS) or **Ctrl+Shift+V**
(Windows/Linux). Any dedicated markdown viewer works the same way. Without a preview you get
the raw source — every fact is there, the scannability is not.

### 4. The browser, for the HTML only

Double-click `views/dashboard_artifact.html` and it opens in your default browser, fully rendered,
no server needed — this is the freshest view after a run finishes locally, since this local file
is generated in the same step as the published copy. Do **not** double-click `dashboard.html` for
this — it is a tombstone stub, kept only to tell you the dashboard moved. Do **not** open the
`.md` files this way either — a browser does not render markdown, so a call prep (or
`views/applying.md`, or `views/conversations.md`) becomes a single run-on wall of text.

### 5. Your profile's private git remote, if you have one

If you followed the backup recommendation and your profile syncs to a **private** git
repository, the hosting site's web view renders markdown files properly — which quietly gives
you a phone-friendly reader for kb files and call preps too, at whatever freshness your last
push was. This route is only as private as that repository; keep it private.

## The morning-of-an-interview case

A call prep exists precisely because something is scheduled soon, so the fast paths matter:

- **At a computer:** route 1 — ask the session for the prep by date or company.
- **On a phone:** route 2 — the conversations section of the dashboard renders the prep as content
  when the call is within the next 7 days (the usual case for "an interview is coming up"); a
  further-out or already-archived prep is an index row there, so open the file itself instead (see
  *A call prep that has already happened*, above).
- **No Claude available at all:** route 3 or 5 — the file itself, in anything that shows
  markdown.

## What this page is not

It does not decide which of these routes is *supported* — they all are; the plugin's files are
plain HTML and markdown exactly so that no single tool owns them. It also does not cover
editing: for changing files by hand and validating afterwards, see
[Your data](your-data.md#editing-by-hand).
