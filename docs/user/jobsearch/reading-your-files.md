# Reading what the search produces

The search writes files that exist to be read by you — company knowledge, call preps, drafts
awaiting your review, and the dashboard. They are not all the same kind of file, and **they do
not all open in the same tool**: the dashboard is HTML and wants a browser, a rendered resume is a
`.docx` and wants a word processor, and everything else is markdown and wants a markdown viewer.
Open one in the wrong tool and you get something readable
but ugly — raw HTML source, or a wall of `#` and `>` markers where formatting should be.

This page says which file opens where, and walks through every realistic way to get at them.

---

## What there is to read

All paths are inside **your profile directory** (the private folder you created at setup — see
[Your data](your-data.md)).

**Starting with 0.32.0, these files sit inside six phase directories** — `presence/`,
`configure/`, `pipeline/`, `applying/`, `conversations/`, `outreach/` — instead of loose at the
profile root. This happens automatically, the first time you open a session after upgrading; you
do nothing to trigger it. The table below gives the path you'll have once that has happened. If
you open your profile folder and still see the old flat names — `kb/`, `call_preps/`,
`drafts.md`, `cover_letters.md` — your next session hasn't run yet; open one and it moves them for
you before you notice.

| file | what it is | format |
|---|---|---|
| `views/dashboard_artifact.html` | **the one published page.** Since 0.71.0 it is cut to what is waiting on a decision from you. Since 0.89.0 it opens with *Today*, the few things that need you now, and every list shows a few rows open, the next ones folded, and the rest counted — see *The page since 0.89.0*, below. Everything else it used to carry has a new home — see *What is on the page since 0.71.0*, below. **A record is shown in full in exactly one place; anywhere else it is a one-line reference that links to that place** | HTML |
| `views/dashboard_artifact_url.txt` | the URL of the published dashboard Artifact above — a link, not a page | plain text |
| `views/presence_set_url.txt` | **retired in 0.71.0.** If you have one it is a leftover: the upgrade queues a "this page is retired" note at that address and then removes the file once the note is confirmed published. Nothing to read there | plain text |
| `presence/rules.md` | **authored by you, not generated** — the settled decisions shown on the *Rules* tab of the resume and LinkedIn reviews. Created once, seeded with three starting rules, the first time you open a session after upgrading to 0.39.0. Unchanged by 0.71.0 | markdown |
| `presence/resumes/*.docx` | **rendered printed resumes** — one file per variant you have asked to be rendered, named `<your-name-slug>_resume_<variant-id>.docx`. Written only when you render one, so a profile that never has does not have this directory at all. Older profiles rendered these to a bare `resumes/` at the profile root — see *Two things that moved out of the profile root*, below | .docx |
| `views/applying.md` | the working queue: roles to apply to, and the follow-up work a submission created. Generated and read-only — never published, regenerated fresh every time you open an application session | markdown |
| `views/conversations.md` | what each upcoming call still needs: whether its prep is written, and if not, that it is **owed**. Generated and read-only, regenerated by the scheduled daily/weekly runs (not only in session) — a `PREP OWED` row is what the search acts on to write the prep before the call | markdown |
| `pipeline/kb/<company>.md` | durable knowledge about one company, e.g. `pipeline/kb/acme-health.md` | markdown |
| `conversations/call_prep_<date>.md` | prep notes for a scheduled call, e.g. `conversations/call_prep_2026-01-15.md`. A note written when full research wasn't available carries `**Prep status:** incomplete — <reason>` under its heading — see below. **Since 0.36.0, a prep for a call already held moves automatically** to `archive/call-preps/` — see *A call prep that has already happened*, below | markdown |
| `outreach/drafts.md` | **since 0.47.0, the working set only** — staged outreach messages still awaiting your review, each carrying a `**Medium:**` line naming how it goes out; see below. A sent or moot entry no longer accumulates here — see *`drafts.md` is a working set, not an archive*, below | markdown |
| `applying/cover_letters.md` | letters, one per role — a letter carrying an unresolved send-hold shows a `**Blocked until:**` marker and is not ready to submit; see below | markdown |

**The dashboard is one page, not a set.** Earlier versions
had one `dashboard.html` that inlined every draft, letter and kb file in full — it grew to
hundreds of KB and kept a local copy that could silently drift from what was actually published. A
version after that split the page into a router, a state view and a phase page per area, published
separately — which turned out to have its own failure: a phase page could publish once and then,
as its item count changed, silently stop being republished while its old URL kept serving a stale
snapshot forever. Now every draft, letter or knowledge file renders as **title + status +
location** on the one dashboard page, its full body living once on that page's own section, and
the whole page republishes together every run so no section's URL can go stale while another's
stays current. The root `dashboard.html` that the split left behind as a pointer is not part of
this any more — it is retired; see *Two things that moved out of the profile root*, below.

### What is on the page since 0.71.0

The dashboard is now a **review-now page**: it holds only what is waiting on a decision from you,
in three lists, each reached from the summary at the top and from a bar pinned to the top of the
page:

- **Drafts to review** — staged messages, shown in full, plus touches that are due and **people
  who are due** (their own section is gone; they are listed here).
- **Opportunities to pursue** — roles where a pursue-or-pass decision is owed. A role the run has not
  finished is not here; it is counted as waiting or as a process failure (see *One lifecycle per role*).
- **Applications to finish** — roles you are pursuing that nothing has been sent for yet, **with
  their cover letters**, which are now shown here and nowhere else.

Everything else that used to be on the page moved. Nothing was deleted from your files; only the
place you read it changed.

| it used to be on the page as | now |
|---|---|
| in-flight roles (applied, in process, parked) and each one's knowledge file path | the status pane, *In flight*; as text, `/jobsearch:status` |
| conversations and commitments, this week and what is owed | the status pane, *This week* and *Preps owed* |
| a call prep's body | the file itself, `views/conversations.md` names it; the page no longer shows a prep body |
| open asks, and the "configure" and "pipeline" asks | the status pane, *Needs you* (soonest act-by date first) and *Open asks* |
| channels | the status pane, *Channel reviews (cadence)* (every channel is listed, the ones due for review first; "due" here means by each channel's own review cadence, not that a sweep will pick it up today) |
| the knowledge index | the status pane, *Knowledge index* |
| stale resume or LinkedIn text | the *Open items* tab of the two review panes. The status band does not count them |
| the second page (your resume layer and public-profile layer) | `/jobsearch:review-resume` and `/jobsearch:review-linkedin` |
| the router with a count per phase | removed. Under the jump bar the page goes straight to *Drafts*; the status band carries how many items need you, the inbox, the lock and the last run |

**The status pane** is a mod panel inside Claude Code: a one-line band under the prompt and a pane
you open with `/jobsearch:status`. It needs a terminal or the Desktop app on your own machine
(see the README's *Where this runs*). Anywhere a pane cannot be drawn, or with mods turned off,
`/jobsearch:status` prints the same content as plain text, from the same script. The pane draws
nothing in a directory that is not a job-search profile.

The pane's sections, in order: *Needs you*, **Roles to reconsider**, *Inbox*, *Write lock*, *Runs*
and whether they did anything, and then (in the full view) the dashboard, gate health and *Elsewhere*.
*Roles to reconsider* lists roles whose stored pay removal today's rule would not repeat, each with
its old verdict, its new verdict, why, and the command that reopens it; it reads "none" when there
are none, and the band shows "N to reconsider" only when there are some. It only reads: nothing is
reopened for you (see *The pay re-screen* in [Your data](your-data.md)).

**On a phone.** The dashboard Artifact still opens there, with its three lists. The status pane
and the review panes are not drawn on a phone. Whether `/jobsearch:status` typed from a phone
works over Remote Control has not been tested, so do not rely on it. One loss is real: a call
prep's text is no longer on the page, so before a call you need a chat turn (ask for the prep by
date or company) or the file itself.

### The page since 0.92.0: why each row is there, and what is left out

0.92.0 keeps the 0.89.0 layout (below) and changes what the lists hold and how they explain themselves.

**Buttons copy text, and say so.** Every button now reads *Copy <what> for N* (for example *Copy Work through for 5*, *Copy
Yes for 10*), or *for the ticked ones* once you tick rows. After a click it reads "Copied. Paste it into your jobsearch session
in Claude Code." One note, placed once after *Today*, says the rest: nothing is recorded until you paste the text into your
jobsearch session in Claude Code, on your computer or its Remote Control session; a plain claude.ai chat cannot record it. A
click on the page itself records nothing.

**Network: who is listed, and why.** Each row under *They wrote back* and *Awaiting a reply* now says when they wrote (and how
many days ago), the role it is about and whether that role is still live (or "about no role"), what a reply serves (your
application, a role you are pursuing, a way in at a target company, or the relationship), and the next step.

- **A reply owed ages out.** Someone who wrote back more than `network.reply_owed_days` days ago (60 unless you change it),
  with no reply drafted, is no longer listed. Exactly 60 days old is still listed.
- **An ended role drops out.** A thread about a role that has ended is not listed.
- **Not listed is named, not hidden.** After *Awaiting a reply*, one closed fold, *Not listed*, counts and names everyone left
  out and why: who wrote back more than N days ago, whose role has ended, and whom you stopped following. These are plain lines,
  with no tick box.
- **A possible duplicate is one row, never merged.** When two records look like the same person (same email, or the same name,
  with or without the same employer), the page shows one row with a line "possible duplicate of {name} (same email, different
  name; ...)". Nothing is merged for you. To settle it, merge the records (`record.py merge-person`) or record that they are
  different people (`not_same_as`); either removes the flag.
- **Stopping and resuming.** To stop following up with someone, say so to the coordinator: it runs `record.py stop-following`
  (dry run first), and they leave both groups until they write again or you write to them. If they come back, their row says
  "back on this list: they wrote on {date}, after you stopped following on {date}". `--undo` resumes. See *Stopping follow-up
  with a person* in [Your data](your-data.md).
- Someone with a draft staged, or a message queued in the outbox, is not listed here: their draft is on the page instead.

**Targets.** Each company row lists up to three of its open role titles, the ones that match your target titles first, then
"+K more", and how many match. A company whose every sighting came through a recruiter channel, with no role on its own
postings, is left out as a staffing firm and never raised; it carries a tick box under **These are employers**, so a wrong
call costs one tick. The heading says "Companies the engine can identify as aggregators or staffing firms are not listed."
only when that check ran on every listed company; when a sighting's channel is unknown it says how many could not be checked
instead.

**Held roles** (called *Roles waiting on a company decision* until 0.93.0) is a section after Targets. Since 0.94.0 a role is held for its title, its pay, its place or its company, and the section says which. It lists, role first, each held role whose title matches your target titles, with the first question it failed (*pay below your floor*, *place outside your criteria*, *criteria not checked*) or, for a role at a company you have not decided about or are watching, why that company holds it: title, company, when it was first seen and the reason. A role at a company you passed on is only counted. The first row of each company has a tick box for that company under *Copy the "Target these companies" request for N*. Above the rows, one line gives the held count, split by company answer (not yet decided, watching, passed on, or pursued with a role that does not meet your criteria) and then by the first question failed (*off title*, *pay*, *place*, *company passed*, *criteria not checked*), and its change since a week ago ("+9 since {date}", "no change since {date}"). Until there is a count from a week ago it says "counting since {date}" (the first week after the upgrade), or "no count from a week ago yet". With no target titles configured nothing is listed and the line says why. A closed fold states the three caps between a find and a decision, in order. Companies holding a matching held role are also put to you first. A role that meets your criteria is **not** on this list: it is read and comes to you to decide (see [How it works](how-it-works.md#a-role-that-meets-your-criteria-is-shown-whatever-its-company-since-0940)).

### The page since 0.89.0: Today first, three levels, tick boxes

**A LinkedIn warning, since 0.94.0.** While the scheduled LinkedIn search is off because LinkedIn showed a warning, one line at the top of Today says so: *LINKEDIN WARNING {date} ({kind}[, reason={word}]): scheduled LinkedIn search is OFF.* followed, where the plugin was in doubt rather than sure, by a sentence in words (for example that it may be a layout change or a search with no results, and is treated as a warning), then *Open LinkedIn yourself and look.* It is there only while the search is off, and it stays until you tell Claude you have looked and name that warning's date. The same line is the first line of every run summary and of the coordinator's start. See [How it works](how-it-works.md#the-linkedin-job-search-since-0940).

**Today leads the page**, and `Today` is the first entry in the bar pinned to the top. It shows at most five things,
in a fixed order: someone is waiting on you first (they wrote back, they accepted, a draft is ready, a chat only you
can record), then what unblocks the search (a role to decide, a posting only you can read, an application to finish,
companies to answer), then upkeep. Each line links to its row further down. When one kind has more than two members,
it is one line ("Did it happen? Coffee with ... and 14 more"); what does not fit is one *Also below* line with each
remaining kind's count. The heading says when the page was made (`Today · as of 18 Nov, 09:12`), because on a phone
you may read it hours later. When nothing needs you, Today is one sentence instead, made only of counts above zero,
for example "Nothing needs a decision from you right now. 41 unread roles are at companies not yet put to you."

**Every list has three levels.** The first few rows are open (5 drafts, 3 per Network group, 5 opportunities, 5
applications, 3 roles to read, 3 to reconsider; Targets shows your weekly number). The next 20 are one-line rows in
one closed fold under the list. Past that, a line says "+ N more ... that are not on this page" and gives the
sentence to say to the coordinator to see them. A row Today links to is always open, never folded. Each heading says
"showing N of M", and the bar shows each list's whole count. The filter chips are gone: with short lists there is
nothing left to filter.

**Drafts are grouped by who they wait on:** *Ready to send*, *Needs you* (with the reason in plain words), and one
closed fold for drafts **waiting, with nothing for you to do** ("2 held, waiting on their reply · 7 queued, waiting
for a mailbox check"). Every draft's text is on the page once, in a closed fold on its row.

**Network groups:** *They wrote back* (a person replied and no reply is drafted; since 0.92.0, within the last
`network.reply_owed_days` days, above), *To record*, *Applied, no one
contacted yet*, *Awaiting a reply*, *Introductions* and *Relationships due this week*. A person who wrote back is
under *They wrote back* even when they are also an introduction you are waiting on. *Awaiting a reply* is split by
how long it has been: *They accepted*, *Went quiet recently* (your last message is at most 21 days old with the default
settings),
*Quiet for a long time* (a fold and a count only, never on Today), and *Not checked yet* (one line: those wait for a
mailbox check, and there is nothing for you to do).

**Targets** is one line per company: its name, its open roles (since 0.92.0, with up to three titles) and when it was raised. The staffing question is asked
only when there is a reason to doubt the company is an employer (every sighting came through a job board or a
recruiter, or it has many open roles in unrelated kinds of job). Then the rows it applies to carry one extra button,
**These are staffing firms**. Companies already left out as staffing firms or aggregators are one counted, closed fold;
those left out only because of their name, or since 0.92.0 because every sighting came through a recruiter, carry a tick box
and one button, **These are employers**. **Yes asks how
motivated you are about each company, 1 to 5**, before anything is recorded: the coordinator asks you, and never
picks the number (on 0.88, every Yes from the page failed and recorded nothing).

**Acting on the page: tick boxes and one button per list.** Each row you can act on has a tick box, and each list or
group has one button (*Work through* for most lists, *Draft replies* or *Draft messages* in the Network, *Yes*, *No*
and *Later* in Targets; since 0.92.0 each reads *Copy ... for N*). With nothing ticked, the button takes the open rows; tick rows, including folded ones, and it
takes exactly those. Today's items start ticked. The button copies one block naming every record, and records nothing. Paste it into your
coordinator session: for *Work through*, the coordinator goes through the records one at a time, asks the one
question each needs, and records your answer; for a write such as *No*, it ends with one line, for example
`applied 3 of 4 (1 refused)`, and tells you why the refused one was refused. Rows past the fold are not in the block,
and the block says how many. If your browser will not let the page copy, the block appears in a box below, already
selected: "Copy the selected text, then paste it into your session." Nothing is sent from the page.

### The resume and LinkedIn reviews (since 0.71.0)

`/jobsearch:review-resume` and `/jobsearch:review-linkedin` replace the second published page. Each
opens a review of one layer with these tabs: the claim union, one tab per declared variant (resume
variants for the first; public-profile variants, each field measured against its recorded
character cap, for the second), **Open items**, and **Rules** (your `presence/rules.md`). A variant
whose surface is not declared shows in both. In the pane, **Revise with Claude** asks the
coordinator to hand that variant to the profile optimizer, and **Render** (resume only) runs
`/jobsearch:resume <variant>`. The pane itself writes nothing. Without the pane, the same command
prints the review as text. You cannot leave a comment on a review the way you could on the old
page: say the correction in chat or use **Revise with Claude**.

If you published the old presence page, its address now serves a short "this page is retired" note
naming both commands. The upgrade queues that note, and the next coordinator session publishes it.

### What the page follows (0.71.0)

One rule runs through the whole page: **a role, a draft, a channel or a person is shown in full in
exactly one list, its own. Anywhere else it comes up, you get a one-line reference with a link to
that row**, never a second copy that could disagree with the first. Every link on the page lands on
something that is on the page.

- **A bar pinned to the top of the page** has three entries, **Drafts to review (N)**,
  **Opportunities to pursue (N)** and **Applications to finish (N)**, and jumps to a list from
  anywhere on the page. A list with nothing in it shows its entry greyed, with no link. Since
  0.88.0, **Network (N)** and **Targets (N)** follow the first entry and, like **Reconsider (N)**
  (only when a role is flagged, below), appear only while their list exists. Since 0.89.0 **Today**
  comes first; it is greyed, with no link, when Today is the one sentence.
- **Roles to reconsider** (since 0.74.0) is a fourth section that exists only when there is
  something to say. Each entry shows a removed or decided role, the verdict stored on it, the
  verdict today's pay rule would give, why, and, in plain words, what to tell Claude to reopen it
  (as pursue or parked) and to record that you screened it. The page
  changes nothing itself. If the check could not run, or could not read a role, the section says so
  rather than disappearing.
- **Drafts to review** shows each staged message, its full text in a closed fold, grouped by who it
  waits on since 0.89.0 (see *The page since 0.89.0*, above). Since 0.88.0 it lists drafts only: the "no draft yet, <why>" rows for a
  touch that is due, an application with no follow-up drafted, and a person who is due are gone,
  and **People due** is retired. Who needs a next step is the **Network** list. The filter chips that narrowed the list are
  gone since 0.89.0.
- **Network** (since 0.88.0) is your communication plan: one row for each person or role that
  needs a next step, in groups (since 0.89.0: They wrote back; To record; Applied, no one
  contacted yet; Awaiting a reply, split four ways; Introductions; Relationships due this week),
  each with who, why, the last touch and a suggested next step. Contact with a person by any route clears an owed follow-up on an
  application, and one that nobody answers expires after `network.owed_followup_days` days
  (7 to 90, default 30). An expiry is listed once under that week's "Expired" line and said once in
  the first run summary after it. How the network is going (reach-outs against budget, chats held,
  introductions) is in the weekly review, not here. Nothing on the page sends anything.
- **Targets to review** (since 0.88.0) is a short weekly list of companies you have not yet
  answered: tick companies, then **Yes**, **No** or **Later** (Yes asks how motivated you are, 1 to
  5). The staffing question is asked only when there is a reason to doubt (see above).
  Aggregators and staffing firms are left out, **later** hides a company for the rest of the
  week, and a counted line says how many more are waiting or snoozed.
- **Every action on the page is plain words, never a command.** A button copies a block that names
  the records (since 0.89.0, the rows you ticked), says what you are asking, and starts by naming
  the jobsearch coordinator. Paste it
  into Claude Code on the machine that holds your search. Pasted anywhere else (claude.ai, or a
  second machine on an older version), nothing is written, because that session cannot see your
  files.
- **Opportunities to pursue** lists only roles where a pursue-or-pass decision is owed. Since 0.87.0 that means roles the plugin has finished reading and researching (*ready*); a role held (for its title, pay, place or company), a duplicate of another role, or one still being read or researched is not listed. Since 0.94.0 each role carries **one short line saying why it is here**, in place of the pay-and-place line and the posting line: the title it matched, the pay and who stated it, the setting, how long ago it was posted, and whether the employer's own posting was checked, for example *Head of Widgets matches "Head of Widgets" · 300-350K stated ≥ 250K · remote · 2 days · not checked*. Anything that was not read says so (`pay not stated`, `setting not stated`, `employer posting: not checked`); nothing is guessed. The full form is one click away in the card's closed detail. The older
  **Show** and **Whose** choices (your move, in live conversation, sent, in interviews, parked,
  ended) are gone, because those roles are not on this page: roles in flight are in the status
  pane, *In flight*, and an ended role is simply not shown.
- **Applications to finish** lists roles you are pursuing with nothing sent, then the cover
  letters. A letter held on a condition shows as a **Held** row and is not ready to submit.

The page republishes whole every run, and a check run with it reads your files and the page
together and fails if a record appears in full twice, a reference points at nothing, a link has no
destination, or a record the page no longer shows is missing from the place it was moved to.

### One lifecycle per role (since 0.82.0)

Every role the search finds goes through the same steps, in order: it is **found**, its **job description is
read**, it is **screened** against your rules, and if it passes it is **researched**. Where a role is in that
sequence is worked out from what is recorded about it; nothing is typed in by hand. A role reaches
**Opportunities to pursue** only when all of that is done. Until then it is not waiting on you, and it is
not hidden either.

**How a run works.** A daily run takes on up to `search.company_intake_per_run` target companies (10 unless you
changed it, since 0.86.0; before it the count was roles, in `search.intake_per_run`) and finishes every waiting role
of each company it takes on. While older unread roles are still waiting, part of those places is held for roles found
since, so new finds are never starved by a backlog. Every role at a target company that is not removed gets its
job description read. A role at a company you have not chosen to target is **held for company**: kept and counted,
not read (see *Held roles and the Network list*, below). Only the roles the screen keeps (*keep*) are researched. Pay, work setting and
location that come off a search-result card are **provisional** until the description is read: a card's
screen never says *keep*, and the description's own pay and setting replace the card's.

**Anything a run took on and did not finish is a process failure, not a quiet delay.** It is shown, with its
cause and how old it is, in these places:

- the **dashboard**: a healthy pipeline shows nothing between the jump bar and *Drafts*; an unhealthy one adds a
  single alert line at the top that links to the *Pipeline state* block, collapsed at the bottom of the page beside
  the conservation line. Open it for the *Process failure* group, the oldest failed roles and each one's cause, and
  every open run. `PIPELINE NOT CHECKED` always shows at the top. (`/jobsearch:status` is unchanged.)
- **Your Move** (the status pane);
- the **start line** of the coordinator session;
- the **headline** of the run summary, as `PROCESS FAILURE: N`.

Since 0.94.0 the *Pipeline state* summary reads `N roles to decide (M at companies you have not chosen)` where it used to read `N ready`, so you can see how many of the roles waiting for you came from a company you never answered about.

Roles not yet taken on are counted and aged as **waiting for intake**, which is not a failure: nothing says a
run ever tried them. The start line reads like this, with made-up numbers:

```
PIPELINE 6 ready · 2 your read · PROCESS FAILURE: 3 (oldest 5d: run-died 2, challenge 1) · WAITING FOR INTAKE: 11 (oldest 2d) · intake 10 companies/run
```

Each cause in the list says what happened and what to do about it. A few you may see: `run-died` (the run
that took the role on never ended), `deadline-reached` (it ran out of time before reaching the role),
`challenge` or `render-failed` (the posting showed a bot check or would not display; it is retried first
next run), `pane-hidden` (since 0.85.0: the Browser pane was hidden, or the reader's tab was not in front, so the page was never read. This is not a fault of the role and never counts toward a stop. The role is *held*, taken after retried and returned roles, and the run summary says `HELD: <n> ...`; after three such runs in a row it moves to your read and is retried only on a run you attend. Show the pane during a run, or see [Posting fetch](posting-fetch.md)), `agent-returned-nothing` (a reader or researcher was started for it and recorded nothing),
`capture-refused`, and `retry-stopped` (runs in a row left it unfinished: three for a cause about the run, two for a cause about the role, usually a page that hangs
the reader; read it yourself, or report it).

**Old unread roles stay failures until they are read.** Roles found before 0.82.0 that nobody read are
labelled `LEGACY BACKLOG` and are counted inside the process-failure total. They are taken on oldest first,
and the run says when it holds places back for new roles.

**Roles only you can open ("your read").** Some postings the plugin never opens or cannot: a board you open
yourself (see below), a role with no address at all, or a page behind a sign-in. These come to you as
**Your read**, in their own list on the page, with the reason. Open the posting, then record what it says
with `record.py read-jd <id> --via candidate`, quoting a line that names the role. The next run screens it
with your read.

**Postings that are down.** A posting that is closed or a dead link ends the role's progress as *gone*; the
role leaves the live list and nothing is asked of you. Since 0.87.0 a role is *gone* in two more cases: when the
reader sees the posting page itself say the role is closed, filled or no longer accepting applications (a job board's
"No longer accepting applications" counts, and the reader records the quoted words), and when the employer-posting
check has closed it on two agreeing signals (see *Is the role still open?* in
[How it works](how-it-works.md)). A page that failed to load, or a redirect to a search page, never makes a role
*gone*. If a later read finds the posting open again, the role comes back.

**The conservation line.** The last line on the page adds every role to exactly one group, so nothing can be
lost between lists, for example:

```
ROLES 120 = waiting 11 + in progress 0 + FAILURE 3 + your read 2 + ready 6 + decided 40 + removed 38 + gone 5 + ended 15 + UNCLASSIFIED 0
```

If the roles in your file do not add up to the roles the page accounts for, it says `ROLES MISMATCH` instead
of staying quiet. A role the plugin cannot place at all is counted as `UNCLASSIFIED` and reported, never
dropped.

**When a role is ready for your decision,** the record has the job description read (with where it was read
from), the pay and work setting, the hard screens applied, and a lean. A role the screen removes never
reaches you at all.

- **A lean** is the system's read of a role: `pursue`, `pass` or `ask`, plus one line. It is
  shown on the role's card as advice. **A lean never removes a role and never decides
  for you**; only the hard rules (a stated range below your floor, a place you have ruled out) remove.
- **Likely-pass signals** are phrases you can list in your settings
  ([`screen.likely_pass_signals`](your-data.md#screening--configjsonscreen)), each with a reason. When a role's title, job
  description or company matches one, its card shows a **LEAN** line with your reason. It is
  a reason to look closely, nothing more.
- **A recruiter role that is old or of unknown age defaults to `ask`.** When the screen's age line
  asks for a first move (a role from a recruiter channel older than `search.retained_search_age_days`,
  or with no known age), its lean is `ask` and the line is that first move: "FIRST MOVE: ask the
  recruiter what stage the search is in, before research or letters" (or, for an unknown age, "ask
  the recruiter when the search opened"). The run states a different lean only when the job
  description gives a reason, and says so in the line.
- **A title below your floor leans by pay, and is never removed (since 0.69.0).** If you set
  [`screen.title_floor`](your-data.md#screening--configjsonscreen) and a role's title reads below
  it, the card shows a computed lean: **pursue**, "title below your floor (<floor>), but
  pay is within your range", when the listed pay clears your floor; **ask**, "title below your
  floor (<floor>); check pay before deciding", when pay is not known or cannot be compared. When the
  pay itself is below your floor the pay rule has already removed the role and the title adds
  nothing. Phrases you list for the title field of `screen.likely_pass_signals` (the mandate) show
  as a **LEAN to pass** with your reason, titled `OFF-MANDATE`. In both cases the role stays on the
  page for you to decide.
- **A role whose only addresses are on a board you open yourself is never read by the run (since 0.75.0).** When every
  address a role carries is on a `manual-candidate` board's `board_hosts` (a portfolio board, say), the run does
  not open it and the role comes to you as *Your read* (`manual-board`). Open the posting yourself, or
  record the company's own posting address; the plugin never visits that board.

**A change to your rules sends screened roles back to waiting.** If you change a pay floor, the title floor,
your target titles or a likely-pass phrase, roles screened under the old rules go back to *waiting* with the
note "your screening rules changed" and a later run re-screens them. That is not counted as a failure.

**On upgrade,** roles you had already decided, removed or been shown as ready keep their place. Roles that
were waiting on a read and never got one appear as old unread roles, as above. What the upgrade changes in
your files is described in [Your data](your-data.md#one-lifecycle-per-role--since-0820).

### Held roles and the Network list (since 0.86.0)

**Held for company.** Before 0.94.0 every role a board showed you at a company you had not chosen to target was recorded and then left alone. **Since 0.94.0 only a role that does not meet your criteria, or sits at a company you passed on, is held**; a role that meets them is read whatever its company. A held role is recorded and left alone: it is not read, screened or researched, and it is **not a failure**. The conservation line (the last line of the *Pipeline state* block) counts it as `held N (undecided U · watching W · passed P · pursued Q)`, so the roles still add up (*pursued* is a role that fails your criteria at a company you targeted by pursuing another of its roles). A held role comes back to life when you target its company, or when it meets your criteria after you change them.

**The Network list.** Below *Drafts* the page has a **Network** list, with its own entry in the jump bar. It holds only
what you act on. The groups below are 0.86.0's; the current ones are in *The page since 0.89.0*, above. In 0.86.0 there
were up to five groups, each shown only when it has something in it:

- **Look into these companies**: companies a board find raised, oldest first, with how many more are waiting, each row
  with the three answers (`record.py company-status <company> active-target`, optionally with `--motivation <1-5>` (optional since 0.94.0), `watching`, `passed`);
- **Chats to record**: a chat that is past and that you have not recorded as held or not, and a booking with no chat
  noted, each with the command that answers it;
- **Suggestions to confirm**: a company, plan or cadence the strategist suggested, with `record.py confirm` and
  `record.py decline`;
- **Sends unobserved**: a reach-out draft older than `network.draft_unobserved_days` (14 unless you changed it) that the
  plugin could not see you send, with the two ways to settle it. A draft's age is counted from the date in the
  `**Brief:**` line the plugin wrote into it. A draft whose age cannot be read (`**Brief:** none`, no such line, or one
  that has been edited into something else) is never guessed to be old and never left out: the weekly review and
  `views/network_strategy.md` list it as "age unknown", with the reason, and it still counts against the week's budget;
- **Proposals to finish**: a proposal still in drafting.

Nothing was added above the lists: a healthy page still shows only the title and the *Generated* line between the jump
bar and *Drafts*. The numbers that are status rather than decisions (reach-outs against the weekly budget, chats booked
and held, introductions, the table of how well you know each target) are in the weekly review and in
`views/network_strategy.md`, a page the plugin generates from your records. **Edit your records, never that page.**
`outreach/network.md` is your own notes and is never written by the plugin.

### A sweep that was held, and the counts under it (since 0.69.0)

**Since 0.94.0 a role is held only when its own card does not answer for it.** A cut-short list or a pay filter LinkedIn added is counted as missing coverage and holds nothing that was shown; a search that dropped the work-type filter holds a role unless its card states its setting (a setting word, or "(Remote)" in the place); one that dropped the place filter holds it unless the card states a place that is not just your own address echoed back; an unapplied date window holds it unless the card says when it was posted; a search the plugin could not read holds it. What is held is counted, and what the search did not read is said as not read, never as zero found. Up to 0.93.0, and on a profile the 0.94.0 upgrade has not reached, the rule below applies instead.

When a LinkedIn or board sweep reports that its page was not showing what was asked (a filter
dropped, a parameter you never set, an unapplied date window, a cut-short list), the roles that only
those queries showed are **held** instead of captured. You see it in three places:

- **The run summary's roles line** gains the count and the reasons, for example `... · 2 quarantined
  (filter-dropped ×1, truncated ×1)`.
- **A second line says how each query read**, for example `query reads (board): 12 reached · 10
  clean · 1 filters unread · 1 degraded (truncated ×1) · 2 total unknown`. *Filters unread* and
  *total unknown* mean the sweep could not tell; those are counted and never hold a role. A run
  from before 0.69.0 prints no such line, which is not the same as reaching nothing.
- **`deferred.py --claimable`** lists held items under *QUARANTINED*. The pass's own output
  (`deferred.py --add-roles`) prints `QUARANTINED <url> (q=…: <reasons>)` per held role and a closing
  `HELD N role(s) (quarantined) from degraded queries: …` line.

- **Two more run-summary lines for a batched board sweep (since 0.84.0).** `BOARD BATCHES 2 of 14 (stopped:
  browser-unavailable, 41 remaining)` says how many batches ran and why it stopped (`done`, `budget-spent`, `stopped`,
  or `LEFT OPEN` when the run ended mid-loop). `OWNED BY linkedin-runner: <channels>` lists the channels the board
  worklist left out because the LinkedIn helper owns them, with how each matched (`link`, `channel-id` or `host-label`,
  the last meaning it was matched by its name). A channel that was not swept carries its own reason: `run-budget` (the
  batch cap or time budget ended first), `route-refused`, or `run-ended`, never a bare `other`.

**How a held role is released.** A later sweep that sees it through a clean query releases it
automatically (the line reads `RELEASED`), and it is then captured like any other. Or release it
yourself: `~/.claude/jobsearch/run deferred.py --unquarantine <item id>`. Nothing is dropped or
deleted while it is held.

**The all-clean flag.** `check_runs.py` prints `BOARD SWEEP READS ALL-CLEAN` when the last 7 board
passes in a row each reported every reached query clean. These are the sweep's own reports of what a
page showed, and nothing here can verify them. A sweep that never looks at the page would report
exactly that pattern, so the flag asks you to open one board's results page and compare it with its
query line before trusting the streak. It is advice, and nothing is blocked.

### A role's place, a flag on it, and a folded row (since 0.70.0)

Three things in `opportunities.jsonl` and in the screen's printed lines are new, and each is there to
say how a place was known.

- **`inferred` on a role's location.** Some postings state no work setting. When one gives a
  concrete place anyway (a line such as `Riverton, ST`), the role is recorded as `onsite` with
  `location.setting_source: inferred`, and the screen line for it ends *(onsite inferred: the posting
  stated no setting)*. Read it as "assumed onsite from the place", not "the posting said onsite". The
  assumption is safe to act on only because a role far enough away is as impractical hybrid as onsite.
  If you correct the setting, the role keeps a record of the correction
  (`location.inference_overturned`, with what it was, what it became and the date) and the flag goes.
  A role with no setting and no readable place has no `type` at all and is kept for review.
- **`duplicate_of` on a row.** When one requisition was recorded twice, the duplicate row can be folded
  into the one that stands for the role with `record.py link-sibling <duplicate> --into <kept row>`. The folded row names
  the kept one in `duplicate_of`, its listings move onto the kept row as sightings, and it drops out of
  the undecided list and out of matching. Nothing is deleted, so it is still there to read. A screen
  of a not-yet-folded second listing prints `DUPLICATE of <row>` on its *passed* line and repeats the
  kept row's verdict.
- **`location` on a sighting.** Each sighting may say where that listing placed the role, so a role
  listed in several cities shows every place it was seen. The role is screened at its most favourable
  place. A sighting marked `split_to` was moved to another row when a wrong merge was undone, and no
  longer counts for this one.

The summary line printed after several roles are screened looks like this, with made-up numbers:
`MINIMAL SCREEN SUMMARY 12 screened · keep 5 · remove 4 (geo 3, comp 1, passed 0) · review 3 ·
commute: outside 3, near 2, unresolvable 1`. A role counted *outside* was removed as too far from
every commute anchor; *near* needs a commute estimate from you; *unresolvable* means the place text
could not be read as a place. If the shipped place table is missing you will see `PLACE TABLE MISSING
... distance not checked`, which means no distance was measured at all. How the distance is worked out
is in [Your data](your-data.md#where-a-role-is-and-when-it-is-too-far--since-0700).

### Correcting a draft from a comment on the page (since 0.64.0)

If your published dashboard is shared inside your organization on claude.ai, a reviewer can leave
a comment on it — say, that one phrase in a draft should read differently. **The search never
fixes that by editing the page**, because the page is regenerated from your files and an edit to
it would be lost on the next run. Instead, in a session, the coordinator reads the comment and
turns it into a correction to the draft in `outreach/drafts.md`:

1. It shows you a **before and after** of that draft and writes nothing yet.
2. It applies the change only after you say yes, and only if the text being replaced occurs
   **exactly once** in that draft — a phrase that appears twice, or not at all, is refused.
3. It records the change on the draft as a `**Revised:**` line (date, where the comment came
   from, old text, new text) — see *A line you may see in `outreach/drafts.md`: `**Revised:**`*, below.
4. It regenerates and republishes the page.

Applying the same correction twice is refused, not repeated. A comment it cannot apply is left
open and the session tells you why; it is never marked resolved.

**What this needs.** Claude Code version 2.1.221 or later, a session you are in (not a scheduled
run), and a dashboard shared within an organization — comments do not exist on a private
artifact or a bare public link. **Where any of that is missing, paste the correction into the
session instead** (*"in the Corvid Labs draft, change 'next week' to 'this month'"*) and it goes
through the same before-and-after and the same yes.

**Or use the page's button.** Since 0.89.0, tick the draft and press *Work through* under *Drafts*.
Paste the block into your session: the coordinator shows you each draft and asks whether to send,
change or drop it, and records what you decide. If your
browser blocks copying, the block appears selected below; copy it and paste it. The button only
copies text; nothing is sent from the page. (A page made before 0.89.0 has a **Copy as prompt**
button on each draft, whose block quotes the draft and ends with `<describe the change here>`:
replace that with what should change. The coordinator still reads it.)

**`views/presence_set.html` (0.39.0 to 0.70.0) was retired in 0.71.0.** It was a second published
page that showed what `presence/` looks like rendered. The review it carried is now
`/jobsearch:review-resume` and `/jobsearch:review-linkedin` (see above). The upgrade deletes the
generated page and its ledger, which the engine rebuilds from `presence/` on demand, and keeps the
page's address long enough to publish the "retired" note there.

### Two things that moved out of the profile root

Two files an earlier version of this page told you to look for at the profile root are not there
any more. **Neither move deletes anything**, and both happen on their own, the first time you open
a session after upgrading — you do nothing to trigger them.

- **`dashboard.html` is gone from the root, and stays gone.** It was a tombstone stub — a note
  saying the dashboard had moved — and it was rewritten on every single run, so deleting it never
  worked. The generator no longer writes it, and the upgrade **moves** an existing one to
  `archive/retired-trackers/dashboard.html`. That is true even if the file at that path was
  something you wrote yourself: it moves, unchanged, rather than being deleted. If a file of that
  name is already at the destination, your root copy is **left where it is** and named in the
  upgrade's summary, never overwritten. The dashboard itself is `views/dashboard_artifact.html`,
  and the published page's URL lives in `views/dashboard_artifact_url.txt` — that file is the one
  place to look for the link.
- **Rendered resumes moved from a root `resumes/` into `presence/resumes/`.** The old default put
  them at the profile root, which the engine's own layout audit treats as a place only anchor files
  belong, so rendering a resume made the profile fail that audit. The upgrade moves the files into
  `presence/resumes/`, contents intact; a name already present at the destination is left at the
  root and named rather than clobbered (a rendered resume may be a document you have already
  sent), and a root `resumes/` left empty afterwards is removed. If you had already set your own
  output directory in `config.json`, it is untouched — only the default changed. A profile the
  upgrade has not reached yet keeps reading and writing the old location, so nothing breaks while
  it is pending.

### A marker you may see under a call prep's heading

A prep note written when full research wasn't available (a scan failed, a source was
unreachable) is not skipped — it's written as far as it could go, with a line under its heading:

```
**Prep status:** incomplete — <reason>
```

`views/conversations.md` treats that call's prep as **still owed**, the same as if nothing had
been written at all, so it stays on your radar rather than looking finished. The next capable run
finishes the note in place — never a second file. If you see this marker on a note you're about to
read before a call, treat it as a heads-up that the note may be missing something, not as an
error.

### A call prep that has already happened

Since 0.36.0, a prep dated before today moves out of `conversations/` and into
`archive/call-preps/` on its own, every run — you do not need to remember to archive it, and
nothing you do triggers it. If durable content from the call was never promoted into
`pipeline/kb/<company>.md` before that happened, the archived note gets a `**Promoted:**
unresolved` line appended so the gap stays visible rather than quietly moving out of sight with
the file.

Since 0.71.0 the dashboard does not render a prep at all. A prep is listed in the status pane (*This
week*, and *Preps owed* when one is missing) and in `views/conversations.md`. Open the file itself
to read it.

The datasets (`data/*.jsonl`) are deliberately not in this table — they are for querying, not
reading, and [Your data](your-data.md) covers them. Neither is `.jobsearch/`, a folder you will
also see in your profile: it holds engine diagnostics, not anything about your search, and
[Your data](your-data.md#jobsearch-engine-state-not-your-data) explains what it is.

### `drafts.md` is a working set, not an archive (since 0.47.0)

A sent or moot entry used to just stay in `outreach/drafts.md` forever, under its own
`**Status:**` line. As of 0.47.0 it does not: `precondition.py --prune` removes every terminal
(`SENT` or `MOOT / DO-NOT-SEND`) entry from the file, and the fact it recorded goes somewhere
durable instead — never dropped. Where the entry named a role, its paragraph becomes a
`research_log[]` row on that opportunity (`data/opportunities.jsonl`); where it addressed only a
channel-anchored person with no role, it becomes a `log[]` row on that channel
(`data/channels.jsonl`) instead. If a matching send was already recorded elsewhere (an
`outreach`/`messages` row for the same touch), the draft's paragraph is simply removed rather
than relocated a second time. An entry naming neither a role nor a channel-resolvable contact is
left in place, reported rather than guessed at.

The block of text above your first entry is also no longer something you or an earlier session
wrote — it is **generated** by `precondition.py --format`, marked by an HTML comment, and
regenerated rather than hand-edited when it needs to change.

The 0.47.0 upgrade runs this relocation once, automatically, so your existing `drafts.md` starts
this release already holding only what is genuinely still under review.

## A line you may see in `outreach/drafts.md`

Every draft entry carries a `**Medium:**` line directly under its `**Status:**` line:

```
**Status:** DRAFT
**Medium:** linkedin-message
```

This is not decoration — it is what the dashboard reads to know how the message is meant to go
out (a LinkedIn note, a cold email, a reply in an existing thread, and so on), and it is what its
per-medium counts and filters are built from. From 0.37.0, **the search writes this line for
you** whenever it drafts or changes a message's medium — you should not normally need to touch it
yourself.

**Starting with 0.37.0, upgrading may add or move this line on drafts that predate it.** Earlier
drafts sometimes had the medium named only inside the `**Status:**` line's own text (something
like `**Status:** rewritten shorter. **Medium: linkedin-message** (~40 words, cap 40)`) — a shape
the dashboard's reader was never able to see, so those rows rendered as `medium: unknown` even
though the right value was sitting right there. Where that exact shape exists — one clear,
recognised value, named once, inside the Status line, and no `**Medium:**` line already present —
the upgrade moves it onto its own line automatically, once, and leaves the `**Status:**` line
otherwise untouched.

**What `medium: unknown` on a row means, and what to do about it:** the entry has no `**Medium:**`
line the dashboard can read — either none was ever written, or the medium is named somewhere the
migration could not safely relocate on its own (two mentions, an unrecognised term, or buried
inside other prose). Add or fix the line yourself, directly under `**Status:**`, in the exact
form `**Medium:** <value>` — one of: `linkedin-connection-note`, `linkedin-inmail`,
`linkedin-message`, `email-cold`, `email-reply`, `phone`, `sms`, `other`. Nothing is lost if you
leave it as `unknown` — the draft still sends the same — but the dashboard's medium counts and
filters will undercount it until the line is there.

## A line you may see in `outreach/drafts.md`: `**Revised:**`

When a correction is applied to a draft (see *Correcting a draft from a comment*, above), the
draft gains one line recording it:

```
**Revised:** 2026-10-14 · comment:t-4821 · "next week" → "this month"
```

It is a note about the edit, not part of the message: it is never sent, and it does not change
whether the draft counts as ready, held or sent. (If recording a correction would change that —
for example, removing a phrase that was holding the draft would leave the old phrase quoted on this
line — the step refuses and says so, rather than leave the draft blocked.) The source reads `chat` when the correction came
from you in the session rather than from a comment. Nothing needs doing about it; delete the line
if you do not want the record.

## A marker you may see in `applying/cover_letters.md`

Upgrading to 0.27.0 may add a line under a letter's heading that was not there before:

```
**Blocked until:** unresolved (migrated 0.27.0 from prose)
```

That is not new information. It is a hold that already existed in the letter's own prose — a note
like "wait until they confirm the licensing question" — made structured, so the dashboard can act
on it instead of only a person reading the text. `unresolved` means the hold is real but not yet
machine-checkable: nothing has said **what** it is waiting on.

**What this means for you:** a letter carrying an unmet `**Blocked until:**` line — `unresolved` or
anything else not satisfied yet — renders on the dashboard as a **"Held"** row among the
cover letters under *Applications to finish*, with no inline body, not in the ready rows, even if
you consider the letter itself finished. To clear it:

- replace `unresolved` with the real condition once you know it —
  `**Blocked until:** contact:<id> outcome:<accepted|replied|...>` — and the letter moves to ready
  by itself the next time the dashboard is generated, or
- delete the `**Blocked until:**` line if the letter was never actually held.

The original prose that prompted the marker is left in place beneath it — nothing was deleted, only
made visible to the dashboard as well as to you.

## Which file opens in which tool

This is the part nothing else tells you, so here it is as a table:

| you want to read | open it in | in the wrong tool you get |
|---|---|---|
| the dashboard (`views/dashboard_artifact.html`) | a **web browser** — double-click the local `.html` file, or open its published Artifact link | a text editor shows thousands of lines of raw HTML |
| the working queue (`views/applying.md`), what's owed for upcoming calls (`views/conversations.md`), a call prep, kb file, `outreach/drafts.md`, `applying/cover_letters.md` | a **markdown-rendering viewer** — the desktop app, or an editor with markdown preview | a browser or plain editor shows the unrendered source: readable, but the structure that makes it scannable is gone |
| a rendered resume (`presence/resumes/*.docx`) | a **word processor** — Word, Pages, LibreOffice, or Google Docs after an upload | a plain text editor shows a binary file, not a document |
| an Artifact URL | it is just a link — open the file, copy the URL into any browser on any device | — |

Rule of thumb: **`.html` means browser, `.md` means markdown viewer, `.docx` means word
processor.**

## The routes, cleanest first

### 1. The desktop app's `</>` Code side — recommended

Open the Claude Code side of the desktop app in your profile directory and ask for what you
want: *"show me the call prep for tomorrow"*, *"what is in the kb file for Acme Health?"*,
*"read me the pending drafts."* The session finds the file, renders the markdown properly, and
can answer questions about it — which no file manager can. This is the cleanest route because
it is the same place the search already runs, and it needs no extra tooling.

For the dashboard, ask the session to open `views/dashboard_artifact.html` in your browser, or
use route 2. For where things stand, type `/jobsearch:status`; to see your resume or LinkedIn
text, `/jobsearch:review-resume` or `/jobsearch:review-linkedin`.

### 2. The published Artifacts — best on a phone

Every daily run republishes **one** claude.ai Artifact, the dashboard, at its **stable URL**
(`views/dashboard_artifact_url.txt`). Open it and the summary at the top names the three lists and
a count for each; each name is a link down to its list on the same page. This is the one route that
needs neither the desktop app nor the local folder, which makes it the practical way to check from
a phone **what is waiting on a decision**. **A pending message's full text lives in *Drafts to review*** —
a role is shown in full only in its own list and is a one-line reference anywhere else. Everything
that is not a decision (roles in flight, the week, asks, channels, call preps) is not on this page:
use the status pane at a computer, or ask the session.

The Artifact is **default-private** to your claude.ai account. It shows what the last run
published; for state newer than the last run, use routes 1 or 3. `views/applying.md` (the working
queue) and `views/conversations.md` (what's owed for upcoming calls) are never published this way;
see route 1 or 3 for them.

### 3. The local folder, with a markdown-capable editor

Everything is a plain file, so any editor opens it — but for the markdown to *render* you want
an editor with a markdown preview. VS Code is the common choice: open your profile folder,
select a `.md` file, and toggle preview with **Cmd+Shift+V** (macOS) or **Ctrl+Shift+V**
(Windows/Linux). Any dedicated markdown viewer works the same way. Without a preview you get
the raw source — every fact is there, the scannability is not.

### 4. The browser, for the HTML only

Double-click `views/dashboard_artifact.html` and it opens in your default browser, fully rendered,
no server needed — this is the freshest view after a run finishes locally, since this local file
is generated in the same step as the published copy. There is no longer an `.html` file at the
profile root to double-click by mistake — the `dashboard.html` stub that used to sit there is
retired (see *Two things that moved out of the profile root*). Do **not** open the
`.md` files this way — a browser does not render markdown, so a call prep (or
`views/applying.md`, or `views/conversations.md`) becomes a single run-on wall of text.

### 5. Your profile's private git remote, if you have one

If you followed the backup recommendation and your profile syncs to a **private** git
repository, the hosting site's web view renders markdown files properly — which quietly gives
you a phone-friendly reader for kb files and call preps too, at whatever freshness your last
push was. This route is only as private as that repository; keep it private.

## The morning-of-an-interview case

A call prep exists precisely because something is scheduled soon, so the fast paths matter:

- **At a computer:** route 1 — ask the session for the prep by date or company.
- **On a phone:** the dashboard no longer shows a call prep (since 0.71.0), so ask the session for the
  prep by date or company in a chat turn, or open the file itself through route 3 or 5.
- **No Claude available at all:** route 3 or 5 — the file itself, in anything that shows
  markdown.

---

## What this page is not

It does not decide which of these routes is *supported* — they all are; the plugin's files are
plain HTML and markdown exactly so that no single tool owns them. It also does not cover
editing: for changing files by hand and validating afterwards, see
[Your data](your-data.md#editing-by-hand).
